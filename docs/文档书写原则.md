# 产品文档书写原则

> 适用：`/product-doc` 场景介绍、用户手册生成。定义"写什么"和"怎么写"的判断标准。

---

## 一、文档层级结构

产品文档采用**两层树形结构**：

```
📁 {行业/领域}安全管理               ← 行业解决方案（父级综述）
│
├── {具体业务场景}                   ← 独立场景（子级详情）
├── {具体业务场景}
└── {具体业务场景}
```

- **父级**：一个空文档节点（在语雀中无正文内容），作为导航容器。对应的综述文档标题为 `{行业/领域}安全管理`，放在同级目录下
- **子级**：每个独立场景一篇独立的 `.md` 文件
- **综述文档**独立于父节点存在，是行业视角的"全景说明书"，不参与业务场景的细节叙事

---

## 二、行业分类与命名原则

### 2.1 行业判定第一性原理

**用户群不重叠，就是不同行业。** 一个行业解决方案的判定不看功能实现度（POC 阶段可能只有一个大屏），而看三个维度：

| 判定维度 | 含义 | 验证问题 |
|------|------|------|
| **被管对象不同** | 管的是学校、是工厂、还是小商户——物理上不重叠 | "这两类对象是同一群人吗？" |
| **监管逻辑不同** | 安全管理关注的风险特征完全不同——校园关注"人"（孩子），工贸关注"设备和流程"（机器），小商户关注"场所"（铺子） | "他们的风险特征能用同一套指标体系衡量吗？" |
| **用户认知不同** | 买单的人能不看其他行业的内容，直接判断"这东西跟我的工作有关" | "校长会从工厂安全的目录里找自己需要的内容吗？" |

### 2.2 行业命名规则

**行业名 = 被管对象 + 安全**。不写监管方，不对监管方做假设。

| ✅ 正确 | ❌ 错误 | 为什么错 |
|------|------|------|
| 校园安全管理 | 教育局安全管理 | 管的是学校，不是教育局 |
| 工贸企业安全管理 | 应急局企业监管 | 应急局是监管方，不是被管对象 |
| 小商户安全监管 | 街道小商户管理 | 街道是监管方之一，且"管理"太宽 |
| 危化品企业安全管理 | 危化监管系统 | 行业名从被管对象出发 |
| 高层建筑消防安全管理 | 消防高层建筑平台 | 消防是监管方 |

**为什么监管方不进入行业名？**
- 同一套系统可能部署给不同监管方：小商户安全监管可以给市场监管局用，也可以给街道办用，也可以给物业公司用
- 监管方是部署时决定的，被管对象是产品定义的。行业名应该反映产品定义，不是某一次部署的场景

### 2.3 平台行业分类（当前 + 预留）

```
公共安全管理平台
├── 🏫 校园安全管理          教育局/消防 → 学校
├── 🏭 工贸企业安全管理        应急局 → 工厂/企业
├── 🏪 小商户安全监管          市场监管局/街道/物业 → 小商户/小场所
│
├── （预留）危化品企业安全管理    应急局 → 危化品生产/储存企业
├── （预留）矿山安全管理         应急局 → 非煤矿山
├── （预留）消防重点单位安全管理   消防 → 商场/医院/酒店等
├── （预留）高层建筑消防安全管理   消防 → 高层住宅/写字楼
└── （预留）…
```

**分类始终遵循**：被管对象是什么 → 行业名叫什么。监管方可以被分配到不同行业，但行业名不由监管方定义。

### 2.4 跨行业共享场景

同一业务场景可能适用于多个行业（如动火作业适用于工贸和校园）。处理原则：

| 规则 | 说明 |
|------|------|
| **场景独立存放** | 共享场景放在顶层目录（如 `docs/动火作业管理/`），不属于任何一个行业目录 |
| **行业综述引用** | 各行业综述在"场景覆盖"表格中链接至共享场景 |
| **不重复写** | 一个场景只写一份，不在各行业目录下重复维护 |
| **检查项随行业差异** | 同一流程框架下，工贸侧重管道焊接、校园侧重食堂维修——差异在场景文档内部注明，不影响复用

## 三、判定原则：场景还是行业解决方案？

在开始写文档之前，必须先判定目标内容的定位。**三种类型**的判断标准：

### 3.1 独立业务场景（Scene）

**判定条件**（满足全部三条才算独立场景）：

| # | 判定标准 | 含义 | 验证问题 |
|:--:|------|------|------|
| 1 | **可独立销售** | 该功能可以单独打包成一个 SaaS 模块，客户只买这一个也能用起来 | "一个客户能只买这个吗？" |
| 2 | **用户可感知为独立痛点** | 目标用户在日常工作中能清晰表述这个需求，不需要先理解平台架构 | "用户会怎么说这个需求？" |
| 3 | **有独立操作流程** | 该场景有一套完整的、不依赖其他场景的操作链路 | "有没有一个从来到走的完整流程？" |

**典型示例**：
- ✅ 校园食品安全全链条管控 — 食堂管理员能说"我想管好食材"，入库→留样→出库→陪餐是独立闭环
- ✅ 动火作业管控 — 安全管理员能说"我想管好动火票"，15 步审批是独立闭环
- ✅ 设备台账与保养 — 设备管理员能说"我想管好几百台设备"，设备建档→保养计划→保养记录是独立闭环

**反例**：
- ❌ 校园安全分级管理 — 不能独立卖，用户不会说"我需要分级管理"，它依附于其他场景的数据之上
- ❌ 数据大屏 — 不能独立卖（数据从哪来？），用户不会说"我需要一个大屏"，大屏是已有数据的可视化，不是独立业务

### 3.2 行业解决方案（Industry Solution / 综述）

**定位**：行业视角的"全景说明书"。告诉读者"这个行业的安全问题，我们怎么系统性解决"。

**何时需要写综述**：
- 当同一个行业下有 ≥3 个独立场景时，需要一份综述把它们串联起来
- 综述不替代任何一个子场景，而是告诉读者"你的问题在哪个范围内"

**综述的核心任务**（三件事）：

| 任务 | 说明 |
|------|------|
| **画行业痛点全景** | 用该行业最触目惊心的真实案例勾勒共性痛点，让行业的人看了觉得"说的就是我们" |
| **讲平台方案架构** | 说明平台怎么从架构上解决这些痛点。这里可以放**分级管理体系**（局级 × 校级）、**由事转势**、**督办闭环**等平台级设计 |
| **做场景导航** | 每一个子场景一段话概述，作为入口引导读者进入自己关心的具体场景 |

**综述不写什么**：
- ❌ 不写"典型一天"（那是子场景的事）
- ❌ 不写独立角色表（每个场景的角色不同，综述的角色是跨场景聚合的，具体角色在子场景里）
- ❌ 不深入某一场景的操作细节（不要让综述和子场景抢内容）

### 3.3 平台架构能力（Platform Architecture）

**定位**：不是独立文档类型，而是**嵌入综述中的架构说明段落**。

这些概念不应该作为独立场景出现，而应该作为综述中"平台方案架构"章节的内容：

| 平台架构能力 | 为什么不独立 | 应该放在哪 |
|------|------|------|
| 分级管理（多级监管架构） | 是平台设计逻辑，不是用户直接感知的业务痛点 | 综述 → 方案架构 |
| 由"事"转"势"（数据汇聚机制） | 是信息流动方式，依附于各场景的数据 | 综述 → 联动机制 |
| 红黑榜 / 履职排名 | 是管理手段，排名本身不是独立业务 | 综述 → 监管手段 |
| 督办响应闭环 | 是跨场景的工作流，不能脱离具体隐患/告警单独存在 | 综述 → 联动机制 |
| 数据大屏 / 驾驶舱 | 是已有数据的可视化呈现，不是独立数据源 | 综述 → 方案架构 |

## 四、不同定位的书写逻辑

### 4.1 行业解决方案（综述）

```markdown
# {行业名称}安全管理

> 阅读时长：约 X 分钟
> 目标读者：{行业决策者、管理者}

📊 图示：{行业安全全景图 / 方案架构图}

## 行业痛点全景

{真实事故案例——选最有冲击力的}

{痛点归纳——用表格}

## 平台方案架构

{方案概述——一段话讲清楚平台怎么系统性解决这些问题}

{架构说明——如果有分级管理体系放在这里}

{联动机制——如果有跨场景的能力放在这里}

### 场景覆盖

| 场景 | 一句话描述 | 典型客户 | 详情 |
|------|------|------|:--:|
| {场景 1} | {痛点一句话} | {谁在用} | [→](链接) |
| {场景 2} | {痛点一句话} | {谁在用} | [→](链接) |

## 核心价值

{按决策者视角，而不是操作者视角}
```

**关键约束**：
- 不写时间线（那是子场景的事）
- 不写独立角色表（但可以在场景覆盖表格中提及每场景的关键角色）
- 案例引用 2-3 个，覆盖不同维度的行业痛点
- 结尾的"核心价值"聚焦**行业决策者**（局长、厂长、老板），而非一线操作者

### 4.2 独立业务场景（场景介绍页）

```markdown
# {场景标题 — 以问题或情境命名}

> 阅读时长：约 X 分钟
> 目标读者：{该场景的具体使用者}

📊 图示：{该场景的业务流程图}

## 涉及角色

| 角色 | 一句话职责 | 使用端 |
|------|-----------|:---:|
| {角色} | {职责} | {Web 端 / 移动端} |

## 背景

{该场景对应的行业真实案例}

| 痛点 | 传统做法 | 问题 |
|------|---------|------|

{平台如何解决——一段话的自然叙事}

## 典型一天

### {时间点} ｜ {事件标题}

{叙事}

📷 截图：{描述}

## 核心价值

| 角色 | 价值 |
|------|------|
| **{角色}** | {一句话价值} |
| **全链条** | {全链条总结} |
```

**关键约束**：
- 标题必须是"问题或情境"，不能是"功能名"。用"一次动火，十五道关"不用"动火作业管理模块"
- "涉及角色"精确到本场景的实际使用者，不写无关角色
- "背景"中的案例引用与本场景直接相关（写食品安全不用方城火灾的案例）
- "典型一天"的时间线覆盖本场景所有角色，展示端到端闭环
- "核心价值"最后一个条目固定为"全链条"总结

### 4.3 用户手册（任务级）

```markdown
# {任务标题 — 动词开头}

> 适用角色：{角色}  |  前置条件：{状态}

## 操作步骤

1. **{步骤标题}**
   - {操作描述}
   📷 截图：{描述}

## 完成后的结果

## 常见问题

**Q: {问题}**
A: {解答}
```

## 五、判断流程

每次写文档前，按以下决策树确定定位：

```
要写的这个内容
│
├── 用户能不能说"我需要这个"？
│   └── 不能 → 平台架构能力 → 放到综述的"方案架构"章节
│
├── 它能不能独立卖给一个客户？
│   └── 不能 → 它依附于其他场景 → 放到综述或对应场景中
│
├── 它有没有独立的"来龙去脉"操作流程？
│   └── 没有 → 它是派生能力（如大屏、排名） → 放到综述
│
└── 以上三条全满足
    └── 独立业务场景 → 写独立场景介绍页
```

## 六、常见错误

| 错误 | 问题 | 正确做法 |
|------|------|------|
| 把平台能力当场景写 | "分级管理"不是用户直接感知的业务，放到场景层面会和一线的食品安全、防欺凌等场景混在一起 | 放到综述的方案架构章节 |
| 在一个场景里塞多个场景 | 工贸企业一篇大文同时讲设备、巡查、隐患、动火——读者不知道该关注哪个 | 拆成独立场景，各自成篇 |
| 没有综述，场景之间没有导航 | 几个独立场景并排放着，用户进来不知道该看哪个 | 写一份行业综述，底部做场景导航表 |
| 综述写得像场景 | 综述里写"典型一天"、写详细的操作角色表 | 综述聚焦行业全景和方案架构，不抢场景的内容 |

# 维保任务模块 — 详细设计

## 1. 概述

维保任务模块是维保三层架构（台账→计划→任务）的**执行层**，定义"做了啥"——维保人员现场执行维保操作、记录检查结果、上报故障的完整过程。任务在维保计划启用时自动生成，执行结束后为报告模块提供数据基础。

**涉及角色：** 服务商端（维保人员执行）、业主端（只读查看进度）

**模块定位：**

```
维保三层架构:

  维保台账（What）     维保计划（When & Who）     维保任务（Do）
  ┌──────────────┐      ┌──────────────┐        ┌──────────────┐
  │ 定义设备清单   │──→  │ 定义何时做    │──→    │ 执行做了啥    │
  │ · 系统类别    │      │ 谁来做        │       │ · 签到记录   │
  │ · 设备类型    │      │ · 选择设备    │       │ · 检查结果   │
  │ · 安装地点    │      │ · 分配人员    │       │ · 故障上报   │
  │ · 检查周期    │      │ · 设置周期    │       │ · 完成状态   │
  │ · 分值(权重)  │      │ · 确认 + 启用 │       └──────────────┘
  └──────────────┘      └──────────────┘
                                      │
                                      │ 启用时自动生成
                                      ▼
                               ┌──────────────┐
                               │  维保任务      │
                               │  （执行记录）   │
                               │  签到→检查→完成│
                               └──────────────┘
```

---

## 2. 核心概念

### 2.1 什么是维保任务

维保任务是维保计划的一次具体执行实例：

- **服务商端**：维保人员在计划启用后收到自动生成的任务，现场签到后按**区域→系统**两层分组查看设备，按组勾选"已检查"和"正常/异常"，标记异常时手动录入设备编码及位置
- **业主端**：查看任务的执行进度和完成情况

### 2.2 任务与计划、台账的关系

| 维度 | 与计划的关系 | 与台账的关系 |
|------|------------|------------|
| 生成来源 | 计划启用时自动生成 | 任务继承计划所选的台账项 |
| 分值 | 继承计划汇总的分值总和 | 不可修改（快照固定） |
| 变更影响 | 计划停用不影响已有任务 | 台账变更不影响已有任务 |

### 2.3 任务状态机

**状态定义：**

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| 待执行 | 任务已生成，等待维保人员开始执行 | 否 |
| 执行中 | 维保人员已签到，正在现场检查设备（默认正常，标记异常） | 否 |
| 已完成 | 所有检查项已完成（可含上报的故障） | 是 |
| 已取消 | 任务被取消，不再执行 | 是 |

**状态流转图：**

```
             计划启用自动生成 / 手动生成
                      │
                      ▼
                ┌──────────┐
                │  待执行    │──── 取消 ────→ ┌──────────┐
                └─────┬────┘                 │  已取消    │
                      │                      └──────────┘
                  维保人员签到                    （终态）
                      │
                      ▼
                ┌──────────┐
                │  执行中    │
                └─────┬────┘
                      │
                全部检查项完成
                      │
                      ▼
                ┌──────────┐
                │  已完成    │
                └──────────┘
                  （终态）
```

**状态转移规则：**

| 当前状态 | 可操作 | 目标状态 | 操作角色 | 说明 |
|---------|-------|---------|---------|------|
| 待执行 | 开始执行（签到） | 执行中 | 维保人员 | 签到后进入执行中，开始逐项检查 |
| 待执行 | 编辑执行人 | 待执行（停留） | 维保人员/管理员 | 修改执行人，其他字段不可编辑 |
| 待执行 | 取消 | 已取消 | 维保人员/管理员 | 仅待执行状态可取消，取消后不可恢复 |
| 执行中 | 逐项检查 + 提交 | 执行中（停留） | 维保人员 | 逐项填写，提交后更新进度 |
| 执行中 | 上报故障 | 执行中（停留） | 维保人员 | 上报后产生故障记录，不改变任务状态 |
| 执行中 | 全部完成 | 已完成 | 维保人员 | 最后一项检查完成，自动变为已完成 |
| 已取消 | — | — | — | 终态，仅可查看详情 |
| 已完成 | — | — | — | 终态，仅可查看详情 |

### 2.4 任务命名规则

任务名称自动生成，格式为 **{计划名称}_{版本号}**，版本号从 1 开始自增。

> 无论自动生成还是手动生成，命名规则统一为 `{计划名称}_{N}`。版本号基于该计划已有任务总数 + 1，确保同一计划的不同任务通过后缀区分。

### 2.5 完成率计算

完成率 = 已完成的检查项分值总和 ÷ 任务总分 × 100%

| 概念 | 说明 |
|------|------|
| 任务总分 | 任务生成时继承计划所选台账项的分值总和，固定不变 |
| 已完成分值 | 检查结果已填写（无论正常/故障）的检查项分值和 |
| 完成率 | 仅计算已填写结果的项，未填写的项不计入 |
| 示例 | 总分 100 分，完成 3 项（70 分），完成率 = 70% |

> 上报故障的检查项也计入"已完成"——维保人员已经执行了检查，只是发现了问题。

## 3. 任务生成规则

### 3.1 两种生成方式

任务有两种生成方式：**自动生成**（计划启用时）和**手动生成**（任务列表页主动操作），两条路径走同一套生成逻辑。

| 生成方式 | 触发时机 | 执行人来源 | 适用场景 |
|---------|---------|-----------|---------|
| 自动生成 | 计划启用 / 停用后重新启用 | 取计划默认人员（第一人） | 常规按计划执行 |
| 手动生成 | 任务列表页点击「生成任务」 | 用户自选 | 临时加派、灵活调配 |

**共同规则：**
- 两张路径均继承计划的设备清单、分值总和、签到配置
- 命名统一为 `{计划名称}_{N}`，N 基于该计划已有任务数自增
- 仅"已启用"状态的计划可生成任务

### 3.2 自动生成

触发条件同原设计：计划从未启用→已启用，或已停用→已启用时，自动创建一条任务。

### 3.3 手动生成

任务列表页提供「+ 生成任务」按钮，点击后弹窗选择：
- **计划**（下拉仅列出"已启用"的计划，含企业名和摘要信息）
- **执行人**（下拉列出全部在职人员，必选）

**冲突提示：** 如果所选计划已有"待执行"或"执行中"的任务，弹窗展示黄色提示条列出进行中任务，用户确认后才生成，防止误操作。不阻止生成——同计划可有多任务（如不同执行人各负责部分设备）。

### 3.4 执行人员调整

"待执行"状态的任务支持改派执行人（在任务列表操作列点击「改派」），其他状态不可修改。

"待执行"状态的任务支持取消（操作列点击「取消」，二次确认后状态变为"已取消"），取消后不可恢复。

## 4. 任务执行流程

### 4.1 执行前置条件

| 条件 | 说明 |
|------|------|
| 任务状态 | 必须为"待执行"才能开始 |
| 执行人 | 仅被分配的执行人才能执行该任务（MVP 不做严格限制，但界面上应显示指定执行人） |

### 4.2 签到（开始执行）

维保人员到达现场后点击「开始执行」完成签到。签到界面根据所属维保计划的配置动态展示：

```
┌──────────────────────────────────────────────┐
│  开始执行任务                                  │
│                                              │
│  任务：2026年5月月度维保计划_0518_1            │
│  计划：2026年5月月度维保计划                   │
│  业主：××物业有限公司                          │
│  执行人：张三                                 │
│                                              │
│  ⏰ 签到时间：2026-05-18 09:30:00             │
│  📍 签到位置：××市××区××路××号（业主单位地址）  │  ← 计划勾选"需要位置"时展示
│  📸 [签到现场照片]（点击拍照上传）               │  ← 计划勾选"需要拍照"时展示
│                                              │
│  [  开始执行  ]                                │
└──────────────────────────────────────────────┘
```

**签到规则：**

| 规则 | 说明 |
|------|------|
| 签到时间 | 点击「开始执行」时系统自动记录当前时间 |
| 签到位置 | 如计划勾选了"需要位置"，签到时展示业主单位地址作为参考位置，签到后记录为固定值；未勾选则不展示位置信息 |
| 签到拍照 | 如计划勾选了"需要拍照"，签到时展示拍照上传入口，签到后可上传现场照片；未勾选则不展示拍照入口 |
| 签到后状态 | 任务状态变为"执行中" |
| 人脸识别 | MVP 暂不接入人脸识别，界面预留位置但不强制 |

### 4.3 设备检查（区域→系统两层分组，按组操作）

签到后进入**设备检查**页面。设备按**区域（建筑）→ 系统**两层结构分组展示。**所有设备默认为"正常"状态**，维保人员无需逐台确认——只需按组勾选"已检查"，对发现问题的组标记"异常"并手动录入异常设备的编码和位置。

**交互原则：**
- 分组操作替代逐台操作，大幅降低维保人员现场操作负担
- 默认正常，仅需关注异常，符合实际工作场景（绝大多数设备状态正常）
- 异常设备手动录入而非选择，避免在大量设备列表中查找

**页面布局：**

```
┌───────────────────────────────────────────────────────────────┐

```

**分组操作规则：**

| 规则 | 说明 |
|------|------|
| 分组层级 | 区域（建筑）→ 系统，两层结构。同一区域同一系统下的所有设备归为一组 |
| 已检查勾选 | 每组有"已检查"复选框，勾选表示该组设备已检查完毕 |
| 正常/异常切换 | 每组有状态下拉（正常/异常），默认为正常 |
| 标记异常 | 将组状态切换为"异常"后，需手动录入异常设备的编码和位置 |
| 手动录入 | 设备编码和位置为自由文本输入（不从台账列表选择），适应现场灵活记录 |
| 多台异常 | 一个组可添加多台异常设备，每台可单独删除 |
| 异常清单 | 所有标记为异常的组的异常设备汇总展示在底部"异常设备清单" |
| 撤销标记 | 将异常组状态切回"正常"或删除全部异常设备后，该组恢复为正常 |

**提交规则：**

| 规则 | 说明 |
|------|------|
| 暂存 | 保存当前勾选和异常录入状态，任务保持"执行中"，允许退出后继续 |
| 提交校验 | 标记为"异常"的组至少需录入一台异常设备（含编码和位置），否则提示补充 |
| 提交后 | 所有勾选"已检查"的组 → 组内正常设备自动记录为正常，异常组按录入设备逐条记录异常 |
| 未检查组 | 未勾选"已检查"的组不参与提交，设备视为未检查 |
| 检查结果写保养记录 | 每台设备检查结果保存后，自动写入该设备维保台账详情的保养记录中 |

### 4.4 故障上报

当维保人员将某个检查项的结果选择为"故障"时，立即弹出故障上报表单：

```
┌──────────────────────────────────────────────┐
│  上报故障                                      │
│                                              │
│  关联检查项：火灾报警控制器测试                  │
│  所属企业：××物业有限公司                       │
│  系统类别：火灾自动报警系统                      │
│                                              │
│  故障描述 *  [___________________________]    │
│  （建议 10 字以上，描述故障现象）                │
│                                              │
│  故障图片   [上传图片] （可选）                 │
│                                              │
│  [  取消  ]        [  确认上报  ]              │
└──────────────────────────────────────────────┘
```

**规则：**

| 规则 | 说明 |
|------|------|
| 触发方式 | 任务提交时，deviceResults 中有标记为"异常"的设备时自动弹出 |
| 关联数据 | 自动关联当前检查项、所属企业、系统类别 |
| 故障描述 | 必填，建议 10 字以上 |
| 故障图片 | 可选上传 |
| 确认上报 | 提交后生成一条故障记录（状态为"待维修"），故障进入 M7 故障与隐患模块 |
| 上报后 | 检查项结果保持"故障"标记，不影响完成率计算（已检查即计入完成率） |

### 4.5 提交完成

当所有检查项均已填写结果后：

| 条件 | 结果 |
|------|------|
| 全部检查项已选"正常"或"故障" | 「提交完成」按钮可点击 |
| 有检查项未填写 | 「提交完成」不可点击，提示"还有 {n} 项未检查" |
| 强制图片项未上传 | 提示"请上传现场图片" |
| 确认提交 | 弹出二次确认：`确认提交所有检查结果？提交后任务将标记为已完成` |
| 提交后 | 任务状态变为"已完成"，业主端可见最终完成率和检查详情 |
| 自动生成报告 | 任务完成后，系统自动生成一份报告草案（状态：草稿），服务商可在报告管理中补充结论后提交 |

### 4.6 检查组中间数据结构（groupResults）

任务执行过程中，以"区域→系统"分组为操作单位，使用 `task.groupResults` 暂存：

```js
groupResults: {
  '1号楼|火灾自动报警系统': {
    checked: true,           // 是否已勾选"已检查"
    status: '正常',           // '正常' | '异常'
    abnormalDevices: []       // 正常时为空数组
  },
  '1号楼|消防给水及消火栓系统': {
    checked: true,
    status: '异常',
    abnormalDevices: [
      { code: 'XHSB-1-001', location: 'B1 水泵房', faultDesc: '水泵启动异响，缺少润滑油' }
    ]
  },
  '1号楼|自动喷水灭火系统': {
    checked: false,
    status: '正常',
    abnormalDevices: []
  }
}
```

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `checked` | boolean | 该组是否已勾选"已检查" |
| `status` | string | `'正常'` / `'异常'` |
| `abnormalDevices` | array | 异常设备列表，每项含 `code`（设备编码）、`location`（位置）和 `faultDesc`（故障描述），正常时为空 |

### 4.7 最终检查结果数据结构（deviceResults）

提交时从 groupResults 展开生成 deviceResults（正常组的所有设备标记为正常，异常组的录入设备标记为异常）：

任务执行时将每台设备的检查结果保存在 `task.deviceResults` 中，结构如下：

```js
deviceResults: {
  'HZBJ-1-001': {
    result: '正常',                          // '正常' | '异常'
    faultDesc: '',                           // 异常时的描述
    faultLocation: '',                       // 异常时的位置
    faultId: null,                           // 关联 FAULT_LIST.id（通过故障上报流程写入）
    checkedBy: 'liyang',                     // 检查人
    checkedAt: '2026-05-12 09:30:00',        // 检查时间
  },
  'XHSB-1-001': {
    result: '异常',
    faultDesc: '水泵启动异响，缺少润滑油',
    faultLocation: 'B1 水泵房',
    faultId: 'f-001',
    checkedBy: 'liyang',
    checkedAt: '2026-05-12 10:15:00',
  }
}
```

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `result` | string | 检查结果：`'正常'` / `'异常'` |
| `faultDesc` | string | 异常时的故障描述（取自 groupResults 中用户录入的 faultDesc），正常时为空 |
| `faultLocation` | string | 异常时的故障位置（取自 groupResults 中用户录入的 location），正常时为空 |
| `faultId` | string\|null | 关联的故障记录 ID（M7），正常时为 null |
| `checkedBy` | string | 检查人姓名 |
| `checkedAt` | string | 检查时间（yyyy-MM-dd HH:mm:ss） |

**数据用途：**
- 任务详情页（只读）展示检查结果
- 报告管理（M8）自动生成的报告草案中"检查结果"章节的数据源
- 逐台设备的检查结果可写入 M4 台账中该设备的"保养记录"

> **报告数据预留**：上述结构已覆盖北京市标准《建筑消防设施维护保养报告书》"详细记录"章节所需的核心字段（设备编码→系统类别→检查结果→检查人→检查时间）。标准报告中"检查方法和要求"文本等补充信息可在后续 M10 维保标准库完善后关联补全。

## 6. 数据联动关系

### 6.1 与其它模块的联动

```
维保计划 ──启用时自动生成→ 生成维保任务（继承计划名称、设备列表、分值）
         计划停用──────→ 已有任务不受影响
         计划删除──────→ 关联的任务保留（任务不随计划删除）

维保台账 ──设备变更────→ 已有任务不受影响（快照已固定）
         分值变更──────→ 已有任务不受影响，下次生成任务时反映新分值
         ──任务执行──→ 每台设备检查结果写入该设备保养记录

故障与隐患 ──执行中上报─→ 生成故障记录（来源标记为"维保任务"）
            任务详情───→ 可查看该任务关联的故障记录

报告管理 ──任务完成后──→ 可作为报告的数据来源
```

### 6.2 联动规则矩阵

| 触发动作 | 影响范围 | 效果 |
|---------|---------|------|
| 计划生成任务 | 任务列表 | 新增一条"待执行"任务 |
| 任务签到 | 任务列表状态 | 待执行→执行中 |
| 任务完成 | 任务列表状态 | 执行中→已完成 |
|  | 业主端任务列表 | 完成率、状态即时同步 |
|  | 待办工作台 | 移除该任务的待办 |
| 执行中上报故障 | 故障与隐患模块 | 生成一条故障记录，来源="维保任务" |
| 计划停用 | 任务生成入口 | 停用后不可生成新任务（已有任务不变） |
| 计划重新启用 | 任务生成入口 | 恢复后可继续生成任务 |

## 7. 业务边界场景

| 场景 | 处理方式 |
|------|---------|
| **计划未启用** | 计划在"未启用"状态时无任务，启用后自动生成 |
| **任务生成后计划被停用** | 不影响已有任务，任务可正常执行 |
| **停用后重新启用计划** | 生成一个新任务，与原任务区分（名称追加 _v2 后缀） |
| **多次签到** | 任务执行中如页面关闭或退出，重新进入执行页时不再要求签到，直接进入检查页 |
| **部分检查项未完成时提交** | 「提交完成」按钮不可点击，提示剩余未检查项数 |
| **任务执行中上报故障后** | 任务状态保持"执行中"，继续检查其他项，不因故障打断执行流程 |
| **所有检查项均故障** | 允许提交完成，所有项标记为故障并上报，任务仍标记为"已完成" |
| **强制图片未上传** | 提交时校验，提示"请为 {检查项名称} 上传现场图片" |
| **已被分配但不属于该任务的维保人员尝试执行** | MVP 不做严格校验，仅展示"指定执行人"提示 |
| **检查项数量为 0 的任务** | 任务可正常生成，点击执行后直接显示"该任务无检查项，是否直接完成？" |
| **业主端查看执行中的任务** | 展示已完成项和未完成项，支持查看已填写的检查结果 |
| **网络中断导致提交失败** | 提示"提交失败，请重试"，已填写的数据保留在本地暂存状态 |
| **手动生成为非启用计划** | 下拉仅列出"已启用"的计划，无法对未启用或已停用计划生成任务 |
| **手动生成时计划已有进行中任务** | 弹窗展示黄色提示条列出进行中任务，用户确认后才生成，不阻止 |
| **取消非待执行状态的任务** | 仅"待执行"状态可取消，其他状态操作列不显示取消入口 |
| **改派非待执行状态的任务** | 仅"待执行"状态可改派执行人，其他状态操作列不显示改派入口 |
| **同一计划多次手动生成** | 允许，每个任务以不同版本号后缀区分（_1, _2, _3…） |

# 关系角色结构化方案

> **文档版本**: v1.1 | **日期**: 2026-07-13 | **上游**: [biz-design.md](../biz-design.md) v2.2 + [相关方管理.md](../ai-spec/相关方管理.md) v1.1

---

## 一、问题

应急局大屏的"商业街管理"模块，需要查询两类数据：

```
应急局
  ├── 相关方：万达商业街（role = my_manager/space_manager/business_street）
  │     ├── 下级：星巴克（商铺）
  │     ├── 下级：海底捞（商铺）
  │     └── 下级：...
  ├── 相关方：阳光物业（role = my_manager/space_manager/property）
  ├── 相关方：蓝盾消防（role = my_service_unit/fire_tech）
  └── 相关方：...
```

| 查询需求 | 说明 |
|---------|------|
| **商业街数据** | 从应急局的 N 个相关方中，筛选出"商业街"类型的那几个 |
| **商铺数据** | 拿到商业街企业后，通过已有的下级管理链查其下属商铺 |

穿透查询本身（商业街 → 商铺）已经可用。**卡住的是第一步：无法按角色类型筛选相关方**。

当前 `EnterpriseRelation.role` 存的是字符串路径 `"my_manager/space_manager/business_street"`，要筛选商业街只能：

```sql
WHERE role LIKE '%business_street%'
```

这不是一个可靠的查询方式——字符串匹配脆弱、无法走索引、无法表达"所有空间管理方（不论具体业态）"这类层级查询。

---

## 二、设计决策：角色树即是分类体系

**不在 Enterprise 上新增固定类别字段。角色树本身已经包含了业态信息，把它变结构化就好。**

| 为什么 | 说明 |
|--------|------|
| 避免冗余 | 关联时已经选了"商业街"，不需要另一处再标记一次 |
| 保持一致性 | 延续 v2.0"角色在关系中定义"的理念 |
| 自然扩展 | 新场景（九小场所、医院…）= 角色树加节点，不改 Schema |
| 支持多视角 | 同一企业对不同关联方可被赋予不同角色 |

---

## 三、角色树设计

### 3.1 三级结构

每一级同时承担两个职责：**关系定性 + 类型分类**。

```
L1（关系方向）       L2（管理模式）        L3（具体业态）
───────────────────────────────────────────────────────
my_manager          我的管理方
  space_manager       空间管理方
    business_street     商业街        ← 今天需要区分的类型
    property            物业
    park                园区
    market              市场
    complex             综合体
  group_manager       集团管理方
    chain_brand         连锁品牌
  venue_manager       场所管理方      ← 未来扩展
    hospital            医院
    school              学校
    nursing_home        养老机构
    nine_small          九小场所集中区

my_supervisor        我的监管方
  fire_rescue          消防救援机构
  emergency_mgmt       应急管理部门
  local_gov            属地政府
  industry_regulator   行业主管部门

social_unit          社会单位          ← 叶子节点

my_service_unit      我的服务单位
  fire_tech            消防技术服务机构

my_operator          我的运营方
  operation_manager    运营管理方
```

### 3.2 扩展方式

```
# 新场景：医院管理
my_manager / venue_manager / hospital     ← 树上加一个叶子节点

# 新场景：学校管理
my_manager / venue_manager / school       ← 同上
```

改一处（角色字典），所有按 L3 筛选的查询自动生效。

## 四、数据模型变更

### 4.1 EnterpriseRelation 新增字段

```prisma
model EnterpriseRelation {
  // 现有字段，保留不变
  role        String   // "my_manager/space_manager/business_street"
  roleLabel   String   // "我的管理方>空间管理方>商业街"

  // 新增：从 role 拆解出的三级扁平字段，用于精确查询
  roleLevel1  String   // "my_manager"
  roleLevel2  String   // "space_manager"（无则为 ""）
  roleLevel3  String   // "business_street"（无则为 ""）
}
```

### 4.2 写入规则

前端传完整 `role` 路径不变，后端写入时自动拆解：

```typescript
// 前端传（不变）
{ enterpriseId: 5, role: "my_manager/space_manager/business_street" }

// 后端写入
{
  role:       "my_manager/space_manager/business_street",  // 完整路径，保留
  roleLabel:  "我的管理方>空间管理方>商业街",                 // 保留
  roleLevel1: "my_manager",                                 // 新增
  roleLevel2: "space_manager",                              // 新增
  roleLevel3: "business_street"                             // 新增
}
```

### 4.3 查询变成了精确匹配

```typescript
// 大屏：应急局纳管的所有商业街
await db.enterpriseRelation.findMany({
  where: {
    enterpriseId: 应急局ID,
    type: 'partner',
    roleLevel3: 'business_street'      // ← 精确匹配，可走索引
  }
})

// 大屏：应急局纳管的所有空间管理方（商业街 + 物业 + 园区 + …）
await db.enterpriseRelation.findMany({
  where: {
    enterpriseId: 应急局ID,
    type: 'partner',
    roleLevel2: 'space_manager'        // ← 按管理模式筛选
  }
})

// 拿到商业街列表后，商铺数据走已有的下级管理查询
await db.enterpriseRelation.findMany({
  where: {
    enterpriseId: 商业街ID,
    type: 'subordinate'                // ← 已有的穿透能力
  }
})
```

## 五、角色字典统一管理

### 5.1 当前问题

角色定义散落 3 处，各自维护，容易不一致：

| 位置 | 文件 |
|------|------|
| 后端 Service | `server/src/services/enterprise.service.ts` — `ROLE_MAP` |
| 前端 HTTP Adapter | `src/api/adapters/enterprise-http.ts` — `PARTNER_ROLE_TREE` |
| 前端 DAO Adapter | `src/api/adapters/enterprise-dao.ts` — `PARTNER_ROLE_TREE` |

### 5.2 统一方案

**后端作为唯一真实来源**，前端通过 API 获取角色树：

```
GET /api/admin/dict/relation-roles
→ [
    {
      value: "my_manager/space_manager/business_street",
      label: "我的管理方>空间管理方>商业街",
      level1: "my_manager",
      level2: "space_manager",
      level3: "business_street"
    },
    ...
  ]
```

前端不再本地维护 `PARTNER_ROLE_TREE`。DAO Mock 模式下保留一份精简副本用于离线开发。

## 六、API 变更

### 6.1 相关方列表增加角色过滤参数

```
GET /api/admin/enterprises/{id}/partners
  新增可选参数：roleLevel1, roleLevel2, roleLevel3
```

示例：

```
# 应急局的所有商业街
GET /api/admin/enterprises/1/partners?roleLevel3=business_street

# 应急局所有空间管理方（商业街+物业+园区…）
GET /api/admin/enterprises/1/partners?roleLevel2=space_manager
```

### 6.2 不改的部分

- 穿透查询（下级管理链）已可用，不动
- 关联相关方接口参数不变（仍传完整 `role` 路径）
- `roleLabel` 展示不变

## 七、改动范围

| # | 改动 | 文件 | 说明 |
|---|------|------|------|
| 1 | Schema 新增 `roleLevel1/2/3` | `prisma/schema.prisma` | 三个 String 字段，默认 `""` |
| 2 | 写入/更新时自动拆解 role | `enterprise.service.ts` | `addPartner` / `updatePartner` 中按 `/` 拆分 |
| 3 | 列表查询支持 level 过滤 | `enterprise.service.ts` | `getPartners` 增加 where 条件 |
| 4 | 角色字典统一到后端 | `enterprise.service.ts` | 后端维护唯一 ROLE_TREE，API 输出 |
| 5 | 前端移除本地角色树 | `enterprise-http.ts`, `enterprise-dao.ts` | 改为从 API/字典接口获取 |
| 6 | 存量数据迁移 | Migration 脚本 | 读 role → 拆分 → 回填 level 字段 |

### 迁移脚本

```
对每条 EnterpriseRelation WHERE type = 'partner' AND role != ''：
  parts = role.split('/')
  roleLevel1 = parts[0] || ''
  roleLevel2 = parts[1] || ''
  roleLevel3 = parts[2] || ''
```

## 九、设计决策

| # | 决策 | 结论 |
|---|------|------|
| 1 | 企业分类用新字段还是角色树 | 角色树。关联时已选类型，不重复建设 |
| 2 | role 是保留字符串还是完全拆字段 | 保留 role 字符串 + 新增 level 字段 |
| 3 | 角色字典谁说了算 | 后端为唯一来源，API 输出 |

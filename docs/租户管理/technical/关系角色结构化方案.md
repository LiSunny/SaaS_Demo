# 企业类型 + 关系角色方案

> **文档版本**: v2.0 | **日期**: 2026-07-13 | **上游**: [biz-design.md](../biz-design.md) v2.2 + [相关方管理.md](../ai-spec/相关方管理.md) v1.1

---

## 一、问题

平台采用**自下而上、逐层配置**的操作模型：

```
运营方在商铺详情页 → 加商业街为下级      （商铺说：商业街管我）
运营方在商业街详情页 → 加应急局为相关方   （商业街说：应急局监管我）
```

**当前关联记录只存了 role，描述的是对方角色**：

```
EnterpriseRelation {
  enterpriseId: 商业街
  relatedId: 应急局
  role: "my_supervisor"   // "应急局是我的监管方"——只描述了应急局
}
```

应急局查相关方列表时：知道自己是什么，但**不知道对方是什么类型**。无法区分谁是商业街、谁是物业、谁是维保公司。

---

## 二、核心设计

**一次关联，记两条信息：**

```
商业街 ──关联──→ 应急局
         role = my_supervisor              ← 对方角色（已有）
         initiatorCategory = commercial_street  ← 我是谁（新增）
```

| 字段 | 回答什么 | 谁需要 |
|------|---------|--------|
| `role` | "对方是我的谁" | 发起方自己查列表时使用 |
| `initiatorCategory` | "我是什么类型" | **被关联方**查列表时过滤使用 |

**企业类型存 Enterprise 上，关联时自动携带，不需要手动维护。**

```
Enterprise.category → 创建企业时选一次 → 关联时自动填入 initiatorCategory
```

## 三、数据模型

### 3.1 Enterprise 新增字段

```prisma
model Enterprise {
  // 已有字段...
  category  String?   // 企业类型，字典驱动。commercial_street / property / hospital / ...
}
```

### 3.2 EnterpriseRelation 新增字段

```prisma
model EnterpriseRelation {
  // 已有字段
  type              String   // "subordinate" | "partner"
  enterpriseId      Int      // 关联发起方
  relatedId         Int      // 关联对方
  role              String   // 对方角色路径
  roleLabel         String   // 人类可读标签

  // 新增
  initiatorCategory String   // 发起方企业类型，从 Enterprise.category 自动取
}
```

### 3.3 写入规则

```typescript
// 关联相关方时（运营方在商业街详情页操作）
POST /api/admin/enterprises/{商业街ID}/partners
{
  relatedId: 应急局ID,
  role: "my_supervisor"
}

// 后端写入
{
  enterpriseId:      商业街ID,
  relatedId:         应急局ID,
  role:              "my_supervisor",
  roleLabel:         "我的监管方",
  initiatorCategory: "commercial_street"  // ← 从 Enterprise.category 自动取
}
```

### 3.4 查询示例

```typescript
// 应急局大屏：谁把我当监管方，且是商业街类型？
await db.enterpriseRelation.findMany({
  where: {
    relatedId:          应急局ID,
    type:               'partner',
    role:               'my_supervisor',
    initiatorCategory:  'commercial_street'  // ← 精确匹配，可走索引
  }
})

// 应急局大屏：谁把我当监管方（不论对方是什么类型）
await db.enterpriseRelation.findMany({
  where: {
    relatedId: 应急局ID,
    type:      'partner',
    role:      'my_supervisor'
  }
})
```

## 四、企业类型字典

### 4.1 设计原则

- **字典驱动**，不硬编码枚举
- 创建企业时选一次，全平台生效
- 新场景新增字典项即可

### 4.2 初始值域

```json
[
  { "value": "commercial_street", "label": "商业街/综合体" },
  { "value": "property",          "label": "物业公司" },
  { "value": "fire_tech_service", "label": "维保服务机构" },
  { "value": "government",        "label": "政府监管机构" },
  { "value": "group_hq",          "label": "集团总部" },
  { "value": "shop",              "label": "商铺/社会单位" },
  { "value": "hospital",          "label": "医院" },
  { "value": "school",            "label": "学校" }
]
```

### 4.3 为什么放 Enterprise 而不是 Relation

| | Enterprise.category | Relation.initiatorCategory |
|---|---|---|
| 维护次数 | 创建企业时选一次 | 每次关联都要选 |
| 一致性 | 同一企业只有一个值，不会不一致 | 同一企业 3 次关联可能被标为 3 种类型 |
| 类型变更 | 改一处，全局生效 | 改 N 条关联记录 |
| 冗余 | 无 | 同一信息重复存储 |

## 五、关系角色保留

### 5.1 为什么保留 role

`role` 仍然有价值——它回答的是 **"对方和我的关系方向"**：

| role | 含义 | 典型数据流向 |
|------|------|------------|
| `my_supervisor` | 对方监管我 | 数据从发起方流向对方 |
| `my_manager` | 对方管我 | 数据从发起方流向对方 |
| `my_service_unit` | 对方服务我 | 数据从发起方流向对方 |
| `social_unit` | 对方是独立社会单位 | 数据从发起方流向对方 |
| `my_operator` | 对方运营我 | 数据从发起方流向对方 |

### 5.2 与 category 的职责分离

```
万达商业街 关联 应急局：
  role = my_supervisor              ← 关系方向（它管我）
  initiatorCategory = commercial_street  ← 我是谁

应急局查："谁把我当监管方？"    → 用 role
应急局查："谁是商业街？"        → 用 initiatorCategory
应急局查："谁是商业街且把我当监管方？" → 两者 AND
```

## 六、角色字典统一

### 6.1 当前问题

角色定义散落 3 处：

| 位置 | 文件 |
|------|------|
| 后端 Service | `server/src/services/enterprise.service.ts` — `ROLE_MAP` |
| 前端 HTTP Adapter | `src/api/adapters/enterprise-http.ts` — `PARTNER_ROLE_TREE` |
| 前端 DAO Adapter | `src/api/adapters/enterprise-dao.ts` — `PARTNER_ROLE_TREE` |

### 6.2 统一方案

后端作为唯一真实来源，前端通过 API 获取：

```
GET /api/admin/dict/relation-roles
GET /api/admin/dict/enterprise-categories
```

## 七、API 变更

### 7.1 相关方列表增加过滤参数

```
GET /api/admin/enterprises/{id}/partners
  新增可选参数：role（已有）, initiatorCategory（新增）
```

示例：

```
# 应急局查：谁把我当监管方，且是商业街？
GET /api/admin/enterprises/related-to/{应急局ID}?type=partner&role=my_supervisor&initiatorCategory=commercial_street
```

### 7.2 新增反向查询端点

```
# 被关联方视角（如应急局）查"谁关联了我"
GET /api/admin/enterprises/{id}/related-by?type=partner
```

## 八、角色树简化

去掉原有的 L2/L3 管理类型子分类（这些已移至 Enterprise.category）。role 树只保留关系方向：

```
改前：
my_manager / space_manager / business_street
my_manager / space_manager / property
my_manager / space_manager / park
...

改后：
my_supervisor      我的监管方
my_manager         我的管理方
social_unit        社会单位
my_service_unit    我的服务单位
my_operator        我的运营方
```

类型分类交给 `initiatorCategory`，role 只管关系方向。

## 十、设计决策

| # | 决策 | 结论 |
|---|------|------|
| 1 | 企业类型放 Enterprise 还是 Relation | Enterprise。类型是企业自身属性，一次定义全局生效 |
| 2 | 角色树要不要保留 | 保留但简化。只表达关系方向，类型分类职责归 category |
| 3 | category 是固定枚举还是字典 | 字典。扩展不加代码 |
| 4 | initiatorCategory 手动选还是自动带 | 自动。从 Enterprise.category 取，用户无感知 |
| 5 | 角色字典谁说了算 | 后端唯一来源 |

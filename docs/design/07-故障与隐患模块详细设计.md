# 故障与隐患模块 — 详细设计

## 1. 概述

故障与隐患模块处理平台中所有消防设备故障和安全隐患的**全生命周期管理**，支持双向流转——服务商端维保/巡查中发现的故障通知业主端，业主端自查上报的隐患可指派给服务商处理。两端通过统一的故障记录池实现数据实时同步。

**涉及角色：** 服务商端（维保人员上报+维修处理）、业主端（跟踪督促+自查上报+维修处理）

**模块定位：**

```
                ┌─────────────────────────────────────┐
                │           故障与隐患模块              │
                │                                     │
                │   ┌─────────────┐  ┌─────────────┐  │
                │   │  服务商端    │  │   业主端     │  │
                │   │             │  │             │  │
                │   │ · 维保上报  │  │ · 接收通知  │  │
                │   │ · 维修处理  │  │ · 督促      │  │
                │   │ · 受理指派  │  │ · 内部维修  │  │
                │   │             │  │ · 转发服务商│  │
                │   │             │  │ · 自查上报  │  │
                │   └──────┬──────┘  └──────┬──────┘  │
                │          │                 │        │
                │          ▼                 ▼        │
                │   ┌─────────────────────────────┐   │
                │   │      故障记录（共享数据）      │   │
                │   │  repairBtnStatus 控制操作     │   │
                │   └─────────────────────────────┘   │
                └─────────────────────────────────────┘
```

## 2. 核心概念

### 2.1 什么是故障/隐患

故障与隐患是**同一数据实体**，统一存储和处理：

| 概念 | 说明 | 业务来源 |
|------|------|---------|
| **故障** | 设备运行异常或损坏，需要维修 | 维保任务执行中发现、智慧消防报警触发 |
| **隐患** | 可能存在安全隐患，需要排查整改 | 业主内部巡查上报 |

两端统一称为"故障记录"，在详情中通过"故障来源"字段区分具体来源。

### 2.2 故障来源

| 来源标识 | 说明 | 产生角色 |
|---------|------|---------|
| `MAINTENANCE_TASK` | 维保任务执行中上报 | 服务商端维保人员 |
| `INSPECTION_TASK` | 第三方巡查任务中上报 | 服务商端巡查人员 |
| `SELF_CHECK` | 业主内部自查上报 | 业主端巡查人员 |
| `SMART_FIRE` | 智慧消防设备自动报警 | 系统自动 |

### 2.3 故障状态机

**状态定义：**

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| 待维修 | 故障已提交，等待维修处理 | 否 |
| 维修中 | 已派发维修，正在处理 | 否 |
| 已完成 | 维修完成 | 是 |

**在服务商端的额外状态层（用于区分流转方向）：**

| 状态 | 含义 | 适用场景 |
|------|------|---------|
| 已上报业主 | 服务商维保/巡查中上报故障，已通知业主 | 服务商→业主方向 |
| 待受理 | 业主指派给服务商的故障，等待服务商受理 | 业主→服务商方向 |

### 2.4 repairBtnStatus 控制机制

核心控制逻辑：一个故障记录能执行什么操作，由 `repairBtnStatus` 字段控制。后端根据故障的来源、当前状态、当前登录端计算该字段的值。

**判断逻辑：**

```
repairBtnStatus = {
  canInternal: boolean,    // 是否允许内部维修
  canRelayToEnterprise: boolean,  // 是否允许转发业主端
  canRelayToISP: boolean   // 是否允许转发服务商
}
```

**计算规则矩阵：**

| 故障来源 | 当前端 | 当前状态 | canInternal | canRelayToEnterprise | canRelayToISP |
|---------|--------|---------|------------|---------------------|--------------|
| 维保/巡查上报 | 业主端 | 待维修 | ✅ | — | ✅ |
| 维保/巡查上报 | 服务商端 | 已上报业主 | ✅ | — | — |
| 自查上报 | 业主端 | 待维修 | ✅ | — | ✅ |
| 自查上报 | 服务商端 | 待受理 | ✅ | — | — |
| 智慧消防报警 | 业主端 | 待维修 | ✅ | — | ✅ |
| 智慧消防报警 | 服务商端 | 待维修 | ✅ | — | — |

> 注：canRelayToEnterprise（转发业主端）在 MVP 中无使用场景，预留字段。

**各按钮对应的操作：**

| 按钮 | 效果 |
|------|------|
| 内部维修 | 弹出维修弹窗 → 选内部人员 → 派发整改（维修人员从本企业人员中选择） |
| 转发第三方服务公司 | 弹出转发弹窗 → 选择第三方公司 → 转发（故障转入对应服务商的待受理列表） |

### 2.5 任务与故障的关联机制

当故障来自**维保任务执行中上报**（来源 = `MAINTENANCE_TASK`）时，故障与任务之间存在双向关联：

**故障记录字段：**

| 字段 | 值 | 说明 |
|------|-----|------|
| `source` | `'MAINTENANCE_TASK'` | 来源类型 |
| `taskId` | 任务 ID | 关联的维保任务 ID |
| `taskName` | 任务名称 | 用于展示，如"2026年5月月检维保计划_1" |

**任务记录字段（deviceResults）：**

| 字段 | 值 | 说明 |
|------|-----|------|
| `deviceResults['设备编码'].faultId` | 故障 ID | 异常项上报后写入，用于标识该设备已关联故障 |

**关联关系图：**

```
M6 维保任务                      M7 故障与隐患
┌─────────────────────┐          ┌─────────────────────────┐
│ deviceResults: {     │          │ fault: {                │
│   'HZBJ-1-001': {   │          │   source: 'MAINTENANCE_ │
│     result: '异常',  │──────────│   TASK',               │
│     faultId: 'f-001'│          │   taskId: 't-001',      │
│     faultDesc: '...' │          │   taskName: '月检计划_1' │
│   }                 │          │ }                       │
│ }                   │          └─────────────────────────┘
└─────────────────────┘
```

**联动规则：**

| 触发动作 | 效果 |
|---------|------|
| 维保任务提交时有异常项 | 自动在 M7 创建故障记录，状态为"已上报业主" |
| 故障在 M7 中被维修/完成 | 任务详情页"关联故障"同步更新状态（实时） |
| 任务完成后查看详情 | 可通过"查看关联故障"跳转至 M7 故障详情 |
| 故障状态变更 | 任务侧只读，不影响故障侧流转 |

核心控制逻辑：一个故障记录能执行什么操作，由 `repairBtnStatus` 字段控制。后端根据故障的来源、当前状态、当前登录端计算该字段的值。

**判断逻辑：**

```

  canInternal: boolean,    // 是否允许内部维修
  canRelayToEnterprise: boolean,  // 是否允许转发业主端
  canRelayToISP: boolean   // 是否允许转发服务商
}
```

**计算规则矩阵：**

| 故障来源 | 当前端 | 当前状态 | canInternal | canRelayToEnterprise | canRelayToISP |
|---------|--------|---------|------------|---------------------|--------------|
| 维保/巡查上报 | 业主端 | 待维修 | ✅ | — | ✅ |
| 维保/巡查上报 | 服务商端 | 已上报业主 | ✅ | — | — |
| 自查上报 | 业主端 | 待维修 | ✅ | — | ✅ |
| 自查上报 | 服务商端 | 待受理 | ✅ | — | — |
| 智慧消防报警 | 业主端 | 待维修 | ✅ | — | ✅ |

## 3. 业务规则

### 3.1 故障记录信息

| 信息类别 | 字段 | 说明 |
|---------|------|------|
| **基本信息** | 故障编号 | 系统自动生成，格式：`GZ-YYYYMMDD-NNNN` |
| | 故障来源 | 维保任务/巡查任务/自查上报/智慧消防 |
| | 来源业务ID（taskId） | 关联的具体任务或记录ID（M6 维保任务上报时填入） |
| | 来源业务名称（taskName） | 关联任务的展示名称，如"2026年5月月检维保计划_1" |
| | 所属企业 | 故障发生的业主单位 |
| **故障描述** | 设备类型 | 故障设备或检查项名称 |
| | 系统类别 | 所属消防系统分类（18类） |
| | 故障描述 | 文本描述 |
| | 故障图片 | 可选上传 |
| **状态** | 当前状态 | 待维修/维修中/已完成 |
| | 流转方向 | 服务商→业主 / 业主→服务商 / 内部 |
| **维修信息** | 维修人员 | 执行维修的人员 |
| | 维修指导 | 可选填的维修指导意见 |
| | 维修完成时间 | 状态变更为已完成的时刻 |
| | repairBtnStatus | 控制按钮可用状态（JSON对象） |

### 3.2 故障编号规则

**格式：** `GZ-YYYYMMDD-NNNN`

| 段 | 含义 | 示例 |
|---|------|------|
| `GZ` | 固定前缀 | GZ |
| `YYYYMMDD` | 故障创建的日期 | 20260518 |
| `NNNN` | 当日自增，从 0001 起 | 0001 |

### 3.3 维修处理规则

| 规则 | 说明 |
|------|------|
| 维修人员选择 | 从当前企业人员列表中选择，必选一人 |
| 维修指导 | 可选填，富文本或纯文本 |
| 维修开始 | 派发整改后状态变为"维修中"，记录维修人员和时间 |
| 维修完成 | 维修人员确认完成，状态变为"已完成"，记录完成时间 |
| 维修完成后 | 不可再次修改，详情展示完整维修记录 |

### 3.4 两端可见性规则

| 故障来源 | 服务商端可见 | 业主端可见 |
|---------|------------|-----------|
| 维保任务上报 | ✅（本企业） | ✅（该业主） |
| 巡查任务上报 | ✅（本企业） | ✅（该业主） |
| 业主自查上报（内部维修） | — | ✅（仅本企业） |
| 业主自查上报（转发服务商） | ✅（被指派的） | ✅（仅本企业） |
| 智慧消防报警 | ✅ | ✅ |

### 3.5 Demo MVP 简化规则

| 简化项 | 处理方式 |
|--------|---------|
| 智慧消防报警 | MVP 不实现，仅界面预留入口，标记"即将开放" |
| 第三方巡查上报 | MVP 归入"维保上报"处理，不做额外区分 |
| 督促功能 | MVP 中督促为纯 UI 交互（按钮状态变化+通知提示），不做消息推送 |
| 多个服务商的选择 | 业主转发时，如关联了多个服务商，弹窗中需选择具体转发给哪家 |

## 5. 数据联动关系

### 5.1 与其它模块的联动

```
维保任务 ──执行中上报──→ 生成故障记录（来源=MAINTENANCE_TASK）
         任务完成──────→ 不影响已有故障

业主端自查 ──上报隐患──→ 生成故障记录（来源=SELF_CHECK）
            转发服务商──→ 服务商端待受理列表可见

服务企业管理 ──关联服务商──→ 业主端"转发"时可选的服务商增加
              解除关联────→ 已转发给该服务商的故障不受影响
```

### 5.2 联动规则矩阵

| 触发动作 | 影响范围 | 效果 |
|---------|---------|------|
| 维保执行中上报故障 | 故障列表 | 新增一条待维修故障（来源=维保任务） |
|  | 维保任务执行页 | 该检查项标记为"故障已上报" |
| 业主自查上报（内部维修） | 故障列表 | 新增一条内部处理故障 |
| 业主自查上报（转发服务商） | 故障列表 | 新增一条待受理故障（来源=自查上报） |
|  | 服务商端故障列表 | 即时出现该故障（待受理状态） |
| 业主转发至服务商 | 服务商端 | 故障转入服务商维修流程 |
| 服务商维修完成 | 业主端 | 故障状态同步变更为"已完成" |
| 业主内部维修完成 | 业主端 | 故障状态变更为"已完成" |
| 业主点击督促 | 服务商端 | 该故障标记为"被督促" |

## 6. 业务边界场景

| 场景 | 处理方式 |
|------|---------|
| **同一故障重复上报** | 系统不进行重复校验（同一问题可能在不同维保周期中被发现），每条记录独立处理 |
| **业主转发时无可选服务商** | 提示"当前无关联的第三方服务公司，请先在相关方企业列表中关联服务商" |
| **故障已被维修完成后再收到督促** | 已完成状态不可变更，督促按钮在已完成状态时不可见 |
| **维修中故障再次上报** | 不影响已有维修，新上报生成独立故障记录 |
| **业主自查上报后自行取消** | MVP 不实现"取消上报"功能，操作需谨慎（在后续迭代中补充） |
| **服务商端新增手动上报** | 服务商端可手动上报故障（不依赖维保任务），入口在列表顶部「+ 上报故障」，必填项：所属企业、设备类型、系统类别、故障描述 |
| **业主端列表为空** | 展示「暂无故障与隐患记录」 |
| **服务商受理后长时间未完成** | MVP 不做超时处理，业主可随时查看状态并督促 |
| **智慧消防报警接入** | MVP 不实现，列表页 Tab 位预留但显示"即将开放"标签 |

## 9. repairBtnStatus 计算参考（后端逻辑）

```text
输入：fault.source, fault.status, currentUser.role, currentUser.enterpriseType
输出：{ canInternal, canRelayToEnterprise, canRelayToISP }

逻辑：
1. 如果故障来源是 MAINTENANCE_TASK 或 INSPECTION_TASK：
   - 当前端=业主端，状态=待维修：
     canInternal=true, canRelayToISP=true
   - 当前端=服务商端，状态=已上报业主：
     canInternal=true, 其他=false

2. 如果故障来源是 SELF_CHECK：
   - 当前端=业主端，状态=待维修：
     canInternal=true, canRelayToISP=true
   - 当前端=服务商端，状态=待受理：
     canInternal=true, 其他=false

3. 如果故障来源是 SMART_FIRE：（MVP 预留）
   - 两端均可内部维修，canRelayToISP=true

4. 任何端，状态=维修中或已完成：
   无可操作按钮（仅查看详情）
```

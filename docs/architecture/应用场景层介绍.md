## 一、这一层是什么

**一句话：客户能看懂的"业务功能"——也就是菜单上能看到的东西。**

放在五层里的位置：

```
第 5 层   业务域与场景层  ← 这一层：客户在菜单上看见什么
第 4 层   交互视图层      页面长什么样（卡片 / 大屏 / 列表 / 表单）
第 3 层   业务引擎层      引擎（数字台账、流程编排、规则引擎…）
第 2 层   数据与集成层    数据和对接
第 1 层   平台底座        租户 / 权限 / 审计 / 配置
```

### 关键的认知修正

> **L5 不是"按用户类型分"，是"按业务域分"。**
> 用户类型（监管 / 单位 / 平台）是**场景的属性**（"主要用户"），不是**行分类的维度**。

例如：
- "运营管理"是一个场景，主要用户是单位，但监管也会来看
- "九小场所管理"是一个场景，主要用户是街道办，但商铺业主、监管都参与
- 一个场景可能多个角色参与——但场景本身是**业务活动**，不是**角色清单**

### 唯一的判断标准

| 进 L5 ✓ | 不进 L5 ✗ |
|---|---|
| 业务语言、能落到日常工作 | 英文/类名/技术词 |
| 客户能指着菜单说"我要这个" | 跨业务域共用的能力（→ L3 引擎） |
| 本域多个场景共用，或只服务单个场景 | 平台级基础设施（→ L1 底座） |

### 跟其他层的关系

| 关系 | 一句话 |
|---|---|
| **L5 消费 L3** | 每个场景 = 本域模型与规则 + 多个引擎的配置组合（泛化公式：新业务 = 台账对象 + 表单字段 + 流程节点 + 流转规则 + 校验规则 + 处置策略 + 消息模板） |
| **L5 走 L4 模板** | 每个场景用什么页面（列表 / 表单 / 大屏 / 看板）由 L4 决定 |
| **L5 装在 L1 上** | 每个场景谁能看、谁能改，由 L1 平台底座管 |

> **"零行代码"的准确边界**：场景的**骨架**（对象、字段、流程、规则、消息）确实全部配置得出来，不用写引擎代码。但**不是 0 行代码**——本域自己的模型与规则（隐患分级、维保周期）要写，场景专属的取数口径也要写。判断哪些该写、哪些该沉，见 [§三 三个概念](#三三个概念业务域--场景--域级模型)。

## 二、这一层解决什么问题（用途）

### 2.1 没有这一层会怎样
- 客户问"你们平台有什么功能"，回答变成"我们有数字台账、流程编排、规则引擎…"——客户听不懂
- 演示给领导看的时候，PPT 上写的是引擎名，不是业务场景名
- 客户做采购评估时，无法在你们的产品里看到"我的行业需要的东西"
- 销售讲产品要逐个解释"这个引擎能解决你的什么场景"，**多一道翻译**

### 2.2 有了这一层
- 客户一眼看见 21 个场景名 + 7 个行业包，6 个域分组
- 每个场景都是一个**"能办的事"**（消防设备台账 = 把消防设备录入并跟踪维保）
- 一个新行业客户的诉求能直接对到某个场景："我们学校要搞运营管理" → "我们有'校园运营管理'，配置即用"
- 引擎是资产、场景是产物——资产支撑产物，**不会**反过来

### 2.3 这一层**不**管什么

| 不管 | 归谁 |
|---|---|
| 怎么画页面、用什么组件 | 第 4 层 交互视图层 |
| 怎么判断、怎么流转、怎么通知 | 第 3 层 业务引擎层 |
| 数据怎么存、怎么同步 | 第 2 层 数据与集成层 |
| 谁能看、谁能改、谁操作过 | 第 1 层 平台底座 |
| 租户里来了一单新需求怎么落 | **销售 + 实施**：落场景 = 挑域 + 配域级模型 + 配引擎 + 配权限 + 上线（目标是把**写代码的部分降到最少**，不是绝对 0 行 —— 见 §三） |

## 三、三个概念：业务域 / 场景 / 域级模型

分不清这三个词，后面所有分层讨论都会打架。先定死：

| 概念 | 一句话 | 判据 | 数量 |
|---|---|---|---|
| **业务域** | 一块**地盘**——按"管什么对象、管哪一段事"划分的顶层分类 | 换个行业、换个客户还成立吗？ | 5 个 |
| **场景** | 一件**要办的事**——用户在具体情境下完成的一个业务活动 | 客户能指着菜单说"我要这个"吗？ | 25 个 |
| **域级模型与规则** | 支撑本域多个场景的公共逻辑，不属于任何一个具体场景 | 换个业务域还用吗？ | 每域若干 |

### 域 ⊃ 场景，域级模型横跨其下

```
        业务域（地盘，如「风险防控」）
        ├── 域级模型与规则    ← 横跨本域所有场景，如「隐患分级与闭环」
        ├── 场景 A   防火巡查
        ├── 场景 B   隐患排查治理
        └── 场景 C   危险作业
```

**为什么必须有"域级模型"这一支**：风险防控的三个场景共用同一套隐患规则——巡查发现的问题变成隐患、整改走销号状态机、危险作业审批看风险等级。它**不属于任何一个场景**，却是这几个场景的公共地基。

如果只分"域 ⊃ 场景"两支，这套规则就只能两个去处：塞进 L3 引擎池（让全平台背负一个只有风险防控在用的能力），或者由三个场景各写一遍（改一次要改三处）。两处都是错的。

### 一段业务逻辑该放哪：三个问句

| 问 | 答 | 落点 |
|---|---|---|
| 跨业务域也成立吗？ | 是 | **L3 业务引擎层**（流程编排、动态表单…） |
| 只在本域成立，但本域多个场景都要用？ | 是 | **本层 · 域级模型与规则**（维保周期、隐患分级） |
| 只服务这一个具体场景？ | 是 | **本层 · 场景专属**（某个报表口径） |

**实例**

| 逻辑 | 判定 | 落点 |
|---|---|---|
| 维保周期（每日 / 每周 / 每季） | 只在维保域用，跨不了域 | **域级**，不进 L3 |
| 隐患分级与闭环 | 风险防控域三个场景共用 | **域级**，不进 L3 |
| 流程编排 | 所有业务域都要用 | **L3 引擎** |

> **落错层的代价**
> - 塞进 L3 → 引擎池膨胀，配置界面出现一堆只有一个选项的下拉，用户没法用
> - 全留在场景层 → 同域三个场景各写一遍隐患分级，改一次要改三处
> - 混着都叫"场景" → 新人不知道该参照哪个现有模块，代码评审也判不了对错

### 数量不是设计出来的

| | 现在 | 说明 |
|---|:--:|---|
| 管理场景 | 4 | **谁在用**：监管方 / 社会单位 / 运营商 / 平台方。这是框架图 L5 上行画的东西 |
| 业务域 | 6 | 分域依据：管**物**（消防资源）/ 管**事前的事**（风险防控）/ 管**事后的事**（应急响应）/ 管**受托服务**（运营服务）/ 管**外部监管关系**（监督管理）/ 管**平台自己**（平台运营） |
| 功能场景 | 21 | 本文与开发排期里说的"场景"指这一层：每个业务域下面 3~5 个 |
| 行业解决方案包 | 7 | **正交维度，不是域**。每个包 ＝ 若干功能域的场景组合 |
| 域级模型 | 每域若干 | 随该域的场景增长而增加 |

> **「场景」一词有两个层级，别混**：**管理场景**回答"谁在用"（4 个），**功能场景**回答"具体哪件事"（21 个）。框架图只画前者，每个管理场景卡片里的一段话就是它的功能范围；本文后续所有场景清单、优先级、现状标记讲的都是后者。

> 注意② 风险防控 和③ 应急响应 **都是"管事"，区别在时间轴**——一个在事故之前，一个在事故之后。这就是必须分域的依据，否则两边的场景会混成一团。

## 四、6 个业务域总览

> **分域依据统一为"管什么职能"，不再混用业态维度。**

| # | 业务域 | 它管什么 | 划分轴 | 主要用户 | 场景数 |
|:--:|---|---|:--:|---|:--:|
| ① | **消防资源** | 安全资产的全生命周期（建账 → 维护 → 消耗） | 物 | 单位（EHS）+ 运营商 | 3 |
| ② | **风险防控** | 事故之前的巡控、排查与作业管控 | 事前 | 单位（安全员/班组长）+ 运营商 | 4 |
| ③ | **应急响应** | 事故之中与之后的处置 | 事后 | 单位 + 运营商 + 监管 | 3 |
| ④ | **运营服务** | 第三方受托整体运营（建设 + 值守 + 维保 + 响应） | 受托 | 运营商 / 技术服务机构 | 4 |
| ⑤ | **监督管理** | 监管方视角：检查、督办、报送 | 监管 | 监管机构 | 3 |
| ⑥ | **平台运营** | 平台运营方配置平台本身 | 平台 | 平台运营方 / 技术管理 | 4 |

**总计：21 个功能场景 ＋ 7 个行业解决方案包。**

> **④ 运营服务为什么单列**：它和其他域不在同一维度。前三个描述**活动**（防 / 处置），⑤ 描述**外部监管关系**，而④ 描述**服务关系**——政府或单位把一段安全职责整体外包，运营商承建设施、值守、维保、响应，按合同履约并被考核结算。它的域级模型也是另一套：合同履约模型、派工规则、值守班次。
>
> 代码里的对应物：`navigation.ts` 的「项目管理（社会单位-运营商）」与「技术服务（技术服务机构）」两个导航分组。

## 五、逐域详解

每个域按 **定位 → 场景清单 → 不归它管 → 现状** 说明。

---

### ① 消防资源

**定位**：把"消防资产"从纸面转到线上——**安全资产的全生命周期**：建账 → 维护 → 消耗。

**场景清单**

| 场景 | 主要用户 | 一句话 | 现状 |
|---|---|---|:--:|
| 消防设备台账 | 单位 EHS + 运营商 | 把灭火器/烟感/消防栓等设备录入系统，跟踪维保、到期提醒 | ● |
| 维保管理 | 单位 + 维保服务 | 计划→任务→执行→签字→记录，全过程留痕 | ◐ |
| 应急物资管理 | 单位 | 应急物资的入库/出库/盘点/到期轮换 | ◐ |

**域级模型与规则**：台账模型（对象/关系/生命周期）· 维保周期算法 · 物资出入库规则

**不归它管**
- **值班值守**——它是**人的活动**不是物，受托集中值守归④ 运营服务
- 怎么判断设备是不是该换了（→ L3 规则引擎）
- 维保任务到期怎么通知（→ L3 消息中心 / 任务调度）
- 设备图片存哪（→ L2 对象存储）

---

### ② 风险防控

**定位**：把"事故之前"的隐患找出来、盯住、不让它变事故。

**场景清单**

| 场景 | 主要用户 | 一句话 | 现状 |
|---|---|---|:--:|
| 防火巡查 | 单位（安全员）+ 运营商 | 按点位、按周期巡查打卡，发现问题直接转隐患 | ◐ |
| 隐患排查治理 | 单位 + 运营商 + 监管 | 发现→审核→派发→整改→销号，全流程闭环 | ● |
| 危险作业 | 单位 + 运营商 + 监管 | 动火/高空/临时用电等作业申请、审批、监护、记录 | ◐ |
| 告警与初判 | 单位 + 运营商（值班） | 设备告警接入、自动分级、推给值班员 | ◐ |

**域级模型与规则**：隐患分级标准 · 隐患闭环状态机 · 危险作业审批流

**不归它管**
- 设备异常如何判定（→ L3 规则引擎 条件、判定、结论）
- 隐患逾期怎么升级（→ L3 策略执行 触发、动作、留痕）
- 重大事件怎么通知监管（→ L3 消息中心）

---

### ③ 应急响应

**定位**：把"事故之中"和"事故之后"的处置流程化——预案有版本、演练有记录、出事有指挥。

**场景清单**

| 场景 | 主要用户 | 一句话 | 现状 |
|---|---|---|:--:|
| 应急预案 | 单位 + 运营商 | 预案电子化、按场景版本管理、关联点位和资源 | ◐ |
| 应急演练 | 单位 + 运营商 | 演练计划、签到、过程记录、复盘 | ◐ |
| 应急指挥 | 单位 + 运营商 + 监管 | 出事时一键启动预案：人车资源到位、对接监管 | ○ |

**域级模型与规则**：预案模板库 · 响应分级规则

**不归它管**
- 现场指挥的实时通信（短信/电话能力 → L3 消息中心）
- 报警接入（→ L2 物联接入 + ② 风险防控 告警与初判）

---

### ④ 运营服务

**定位**：**第三方受托整体运营**——政府或单位把一段安全职责整体外包，运营商承建设施、值守、维保、响应，按合同履约并被考核结算。

> 这是唯一一个**按"以谁的身份管"划分**的域，前三个域按活动划分（防 / 处置），⑤ 按监管关系划分。
> 代码里的对应物：`navigation.ts` 的「项目管理（社会单位-运营商）」与「技术服务（技术服务机构）」两个导航分组。

**典型形态**：政府为一个区域集中安装设备，由一家公司整体承建并集中值守运行；运营商承接消防工程项目的建设与运维。

**场景清单**

| 场景 | 主要用户 | 一句话 | 现状 |
|---|---|---|:--:|
| 集中值守 | 运营商 / 技术服务机构 | 一个值班中心同时监控多个单位的消控室与告警，含排班、交接班、巡查打卡 | ◐（消控室大屏已有） |
| 项目交付 | 运营商 | 消防工程建设全过程：计划、进场、实施、验收、移交 | ◐（项目管理模块） |
| 维保派工 | 运营商 + 维保服务 | 合同签订 → 计划生成 → 派单 → 执行 → 签字 → 结算 | ◐（维保应用已有） |
| 运维考核 | 运营商 + 客户 | 响应时效、履约率、服务质量评价与对客结算 | ○ |

**域级模型与规则**：合同履约模型 · 派工规则 · 值守班次 · 服务 SLA 口径

**不归它管**
- 单位自己内部的日常安全管理（→ ① 消防资源 / ② 风险防控 / ③ 应急响应）
- 对运营商的监管与考核（→ ⑤ 监督管理）

---

### ⑤ 监督管理

**定位**：监管方视角——检查、督办、报送。**监管是外部方行为，不属于任何一个被监管的业务域。**

**场景清单**

| 场景 | 主要用户 | 一句话 | 现状 |
|---|---|---|:--:|
| 监管检查 | 监管机构 | 现场检查、取证、整改闭环 | ◐ |
| 督办与考核 | 监管机构 | 超时督办、红黑榜、考核评分 | ◐ |
| 监管数据报送 / 行业风险分析 | 监管机构 | 对上级报送、跨单位风险聚合 | ○ |

**域级模型与规则**：监管指标口径 · 督办规则 · 报送模板

**不归它管**
- 单位内部的管理动作（→ ① ② ③）
- 对服务商（运营商）的履约评价——这一半归 ④ 运维考核，监管侧评价归本域

---

### ⑥ 平台运营

**定位**：把"配平台本身"作为一套场景**给平台方**用——租户、单位、用户、岗位、配置。

**场景清单**

| 场景 | 主要用户 | 一句话 | 现状 |
|---|---|---|:--:|
| 租户与组织管理 | 平台运营方 | 新建客户、新建单位、配置组织层级 | ●（= L1 ①） |
| 用户与岗位管理 | 平台运营方 | 创建用户、配岗位、改权限 | ●（= L1 ②③） |
| 大屏与流程配置 | 平台运营方 + 单位 | 大屏模板配置、类型注册、流程模板维护 | ◐ |
| 系统参数 | 平台技术管理 | 字典、附件、编号规则、主题、菜单、路由、升级 | ◐ |

**域级模型与规则**：无自有逻辑，直接暴露 L1 配置。

**注意**：这一域与 L1 平台底座**大部分重叠**——因为"配置底座"本身就是这一域的内容。L1 写"有"，L5 写"用"，L1 是底座能力，L5 是底座在菜单上暴露的功能入口。对应代码里的两个导航分组：「运营管理（platform-ops）」与「平台管理（platform-admin）」。

## 五之二、行业解决方案包（正交维度，不是域）

**业态不是域**。校园、医院、工贸、沿街商铺——这些是"客户是哪个行业"，与"平台管什么事"正交。

| 行业解决方案包 | 组合了哪些功能域的场景 |
|---|---|
| 校园运营管理 | 消防资源（设备台账）＋ 风险防控（防火巡查/隐患治理）＋ 应急响应（预案） |
| 九小场所管理 | 消防资源 + 风险防控（合规巡查）+ 监督管理（检查） |
| 沿街商铺管理 | 风险防控（自查/整治）＋ 监督管理 |
| 工贸企业运营管理 | 消防资源（设备维保）＋ 风险防控（危险作业）＋ 应急响应 + 运营服务（受托维保） |
| 医院安全管理 | 消防资源 + 风险防控 + 应急响应（危化品、放射） |
| 物业园区管理 | 消防资源 + 风险防控 + 运营服务（受托） |
| 复工复产管理 | 风险防控（排查）＋ 应急响应 + 监督管理（验收） |

**一个解决方案包 ＝ 若干功能域的场景组合**，交付时按行业打包。这也是原「运营与监管」域里 7 个业态场景的去处。

> **为什么必须拆出来**：原来「校园运营管理」被当成一个域，但它里面本身就包含隐患排查——而隐患排查已经在② 风险防控里了，同一个场景被放进两个域。拆成正交维度后，②和④不再抢地盘。

## 六、6 域怎么配合（一条主链路）

```
① 消防资源  →  设备台账里有台账 → ② 风险防控  →  防火巡查发现隐患
                                            ↓ 隐患排查治理
                                            ↓ 触发（条件）
                                            ↓ ② 风险防控  →  危险作业申请
                                            ↓
                                            ↓ 触发（结果）
                                            ↓ ③ 应急响应  →  应急指挥
                                            ↓
④ 运营服务    ←  运营商受托：不自己建，替客户建 + 集中值守 + 维保派工
⑤ 监督管理    ←  监管方从监管检查/督办/数据报送看全过程
⑥ 平台运营    ←  平台方配好上面五个域的租户/用户/权限/字典
```

**关键**：L5 场景**跨域有依赖**。一个完整的"单位日常安全管理"会**同时调用** 4 个域（消防资源 + 风险防控 + 应急响应 + 监督管理）。每个域不是孤岛。

**三种角色，三条不同的路径**：

| 角色 | 走哪几个域 |
|---|---|
| 单位自己管 | 消防资源 → 风险防控 → 应急响应 |
| 运营商受托管 | 运营服务（承建/值守/维保）→ 调用上面三个域的能力 |
| 监管方看 | 监督管理 ← 只读汇聚前面所有域的结果 |

## 七、场景的"组装"——以「火灾隐患排查治理」为例

L5 是 L3 的**消费者**。一个场景怎么"长出来"：

```
L5  菜单上有「隐患排查治理」入口
      ↓ 带上本域自己的东西
      隐患分级标准 + 闭环状态机 + 「五定方案」要求   ← 风险防控域的模型与规则
      ↓ 用到
L4  列表页 + 表单页 + 看板
      ↓ 配出
L3  数字台账（管隐患对象） + 动态表单（排查表） +
      流程编排（整改流程） + 规则引擎（分级判定） +
      消息中心（通知） + 策略执行（逾期升级）
      ↓ 数据放
L2  隐患数据存哪 + 谁可以看
      ↓ 决定
L1  谁能看、谁能改、每步留痕
```

**这 6 个 L3 引擎全部用上，且全部是配置——没有人为这个场景新写引擎代码。**

但场景里仍有**两样不是配置出来的**，必须诚实标出来：

| 不是配置的 | 归哪一档 | 谁写的 |
|---|---|---|
| 隐患分级标准、闭环状态机、「五定方案」要求 | **域级模型与规则**（风险防控域三个场景共用） | 开发，随域演进 |
| 监管报告里的取数口径、挂牌督办清单格式 | **场景专属**（只用这一次） | 开发，用例级 |

所以「9 个引擎撑起 21 场景 ＋ 7 行业包」的准确含义是：**引擎和视图不用为新场景重写**，而不是"零行代码"。省掉的是重复造轮子，不是全部工作量。

## 八、状态与建设顺序

| 业务域 | 现状 | 备注 |
|---|---|---|
| ① 消防资源 | ◐（4 项中 1 已实做） | 设备台账是地基，维保/值班/应急物资待补 |
| ② 风险防控 | ◐（1 已实做） | 隐患排查最成熟；防火巡查/危险作业有菜单占位 |
| ③ 应急响应 | ○（3 项都未实做） | 设计上有预案，**实做**还没有 |
| ④ 运营服务 | ◐（维保应用、项目管理已有雏形） | **受托运营**，代码里对应「项目管理-运营商」「技术服务-服务机构」两个导航分组 |
| ⑤ 监督管理 | ◐（检查/督办已实做） | 监管方只读汇聚，不承载业务动作 |
| ⑥ 平台运营 | ● | 全部从 L1 平台底座直接暴露 |

**施工顺序（自上而下是优先级）**

| 优先级 | 动作 | 为什么 |
|:---:|---|---|
| **P0** | **把"消防资源"和"风险防控"做实**（维保/巡查/告警 → 从占位到能跑） | 大多数客户进来首先用的是这两个域；不实做 = 演示时只展示一个台账 |
| **P0** | **③ 应急响应至少把"应急预案"做出来** | PPT 已承诺；纯结构化录入就能跑 |
| P1 | **④ 运营服务的"集中值守"做成多租户** | 一个值班中心监控多个单位是运营商模式的护城河，目前消控室大屏只支持单点 |
| P1 | **7 个行业解决方案包中的沿街/医院做客户验证** | 没客户需求前不开发，但**有客户需求时不能临时拼** |
| P1 | **把"⑥ 平台运营"的菜单路径理顺** | 现在菜单和 L1 配置项有重叠，路径要分清 |
| P2 | **③ 应急演练 / 应急指挥** | 应急产业链里这两个是"软需求"，按客户走 |

## 九、FAQ

**Q1：场景和"用户类型"为什么不能混？**
A：场景是**业务活动**（运营管理、防火巡查），用户类型是**谁**（监管、单位、平台方）。一个场景常有多类用户参与，**如果按使用方去分行，就会让业务域被角色切碎**——同样的"隐患排查"在监管行和单位行各出现一次，改一次要改两处。

所以结构上**一律按业务域归属**：每个功能场景只属于一个域，全平台 21 个场景在四个使用方卡里也各只出现一次，不重复。

> 框架图 L5 里同时画了「场景 · 谁在用」和「业务域 · 提供什么」两行——上面那行是**视角**，回答"谁在用"；下面那行才是**结构**，回答"这个场景归哪个域、由哪些能力支撑"。两行不是二选一，别把上面那行当成归属划分。

**Q2：行业解决方案包为什么不算"业务域"？**
A：业态与职能是**正交的两个维度**。"校园"是客户是谁，"隐患排查"是平台管什么事。混成一个域会出事：原来"校园运营管理"里包含隐患排查，而隐患排查已经在② 风险防控里了，同一个场景被放进两个域。拆成正交后，每个功能场景只属于一个域，行业包只是它们的组合。

业态之间的合规差异很大（学校有食堂卫生、工厂有危化品、医院有放射科），所以行业包按业态平铺，让客户能**按行业找**——搜索"九小"就能看到"九小场所管理"。

**Q3：L5 场景是从 L3 引擎"配出来的"——是不是意味着 L5 没有开发量？**
A：对，L5 没有**代码级**开发量。但有**配置工作**（每个场景要配一组 L3 引擎）、**内容工作**（排查表怎么设计、应急预案怎么模板化）、**客户化工作**（每个业态的字典/合规项不同）。这些是**实施/配置**的活，不是**研发**的活。

**Q4：图上横版的 L5 5 个角色行要怎么改？**
A：要把"区域监管 / 社会单位 / 运营商 / 服务机构 / 平台运营"五个**角色行**换成六个**业务域行**：消防资源 / 风险防控 / 应急响应 / 运营服务 / 监督管理 / 平台运营。每个域下面挂自己的场景，**主要用户**用角标标注，不分行。注意 **④ 运营服务** 与角色行里的"运营商/服务机构"是巧合同名但不同含义——角色是"谁在用"，运营服务域是"以谁的身份受托运营"。

**Q5：沿街商铺和医院安全是客户需求吗？**
A：团队文档里**没有**这两个词。是按行业惯例加的"应做但还没做"，现在归在**行业解决方案包**里。已标 ◐，等客户验证。

**Q6：运营商受托运营（④）和单位自己管（①③）是不是重复建设？**
A：不重复，是**同一套能力的两种交付形态**。单位自己管 = ②风险防控的场景直接用；运营商受托 = ④运营服务承接合同后，调用同样的 ② 能力去履约，差别在于多了合同、派工、考核这套**履约外壳**。这层外壳只有运营商模式才需要，所以它有自己的域级模型。

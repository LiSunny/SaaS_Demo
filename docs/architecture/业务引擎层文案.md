## 二、编写规则

### 2.1 图面文案（唯一原则）

1. **写"能力要素"，不写"具体做法"。**
   - ✅ `对象、关系、生命周期、指标` —— 框定这个引擎覆盖哪几块能力
   - ❌ `把设备、隐患、物资等都定义成台账` —— 这是做法，等于把实现方式提前钉死
2. **每一项 2–5 字，2–5 项**，不强制各引擎条数一致（策略执行就是三项）。
3. 项与项之间用**顿号**。
4. **不用符号**（`→`、`+`、`/`），**不用英文**（`SLA` 写"时限"）。
5. 术语要能被业务对上号，但不展开解释。
6. **写"这个引擎拥有什么"，不写"它能渲染／消费什么"。** 渲染器不拥有被它渲染的东西 —— 见 5.2。

### 2.2 为什么不用句子（重要，别再改回去）

架构图的作用是**框定能力范围**，不是描述实现方式。

- 写成句子（"条件一满足就自动处置，并留下记录"）看着好懂，但：
  - 把实现方式**提前固定**了，后面业务形态一变，图就要改；
  - 让人误以为"这个能力已经这么做了"，而实际上策略执行还是 ○ 待建；
  - 细节一旦写进架构图，讨论就会被"图上不是这么写的吗"带偏。
- 写成要素（"触发、动作、留痕"）：
  - 只承诺**范围**，不承诺**做法**；
  - 需求进来时能对号入座（"这属于留痕，归策略执行"），但不会限制具体怎么实现。

**所以：图要抽象（框范围），解释放到"讲图话术"里（见第三节），不要放到图上。**

### 2.3 验收标准

图面：不懂技术的人**能对上号**（知道这块能力归谁管）即可，**不要求他光看图就懂全部细节**。
细节由讲图的人现场说 —— 所以讲图话术必须提前准备好。

> **踩过的两个坑（记下来别再犯）**
> 1. 压成"清一色两字词"（对象、关系、节点、指派、校验、分级…）—— 信息量掉一半，看不出引擎之间的差别。
> 2. 改成"一句说清干什么"的句子 —— **太具体，容易把产品设计带进固化**。
> **结论：图面用要素，解释用话术。两头都别越界。**

## 四、讲图话术（不写进图，讲解时用）

被问到"这块具体是什么"时，照下面说。**这里是唯一允许展开细节的地方。**

| 引擎 | 怎么讲 |
|---|---|
| 数字台账 | 设备、隐患、物资、人员都能配成台账；台账之间的关系和状态变化由系统维护，不用改代码 |
| 流程编排 | 谁办、交给谁、多久办完，都在流程图上配；改流程不用改代码 |
| 动态表单 | 业务人员自己拖字段画表单；必填、格式这些校验自动生效 |
| 策略执行 | 满足条件就自动派活、自动升级；每一步都有记录，可回溯可举证 |
| 规则引擎 | 一直盯着某个事项，命中条件就给出结论（该不该、几级、超没超）；它只出结论，不做事 |
| 消息中心 | 站内信、短信、语音三种触达都从这一个出口发；能查有没有送到 |
| 任务调度 | 按周期自动派任务；到点提醒；超时自动催办 |
| 统计服务 | 指标口径只在这里定义一次，看板、大屏、报表、预警阈值都来取同一个数，不会各算各的 |
| 报表引擎 | 拿统计服务的数，套模板成表；月报季报自动出，签完字直接报送监管方 |

### 四项要素的逐条含义（内部对齐用）

| 引擎 | 四项分别指什么 |
|---|---|
| 数字台账 | 对象＝有哪些台账；关系＝谁关联谁；生命周期＝状态怎么走 |
| 流程编排 | 模板＝可复用的流程蓝图；节点＝分几步；流转＝怎么跳转；指派＝谁办；时限＝多久办完 |
| 动态表单 | 设计器＝业务自己画；运行时渲染＝把定义渲染成录入界面；字段校验＝必填、格式 |
| 策略执行 | 触发＝什么条件启动；动作＝自动做什么；留痕＝全程有记录可举证 |
| 规则引擎 | 条件＝盯什么、什么算命中；判定＝怎么算；结论＝算出什么（等级、是否超标、能不能提交） |
| 消息中心 | 模板＝发什么；通道＝站内／短信／语音；送达回执＝发到没 |
| 任务调度 | 周期计划自动生成任务＝到点自动派活；超时催办＝没做就催 |
| 统计服务 | 指标＝有哪些统计项；口径＝每个指标怎么算；取数＝按口径算出来给谁用 |
| 报表引擎 | 模板＝长什么样；出报＝周期自动成表；报送＝签完直接送监管 |

## 五、两条最容易搞错的边界

### 5.1 策略执行 vs 规则引擎

- **规则引擎**只回答"要不要" —— 无状态判断。
- **策略执行**回答"要，然后干什么" —— 有状态闭环：它**调用**规则引擎做判断，再**调用**流程编排派活、**调用**消息中心通知。

所以策略执行只写「触发、动作、留痕」，**"判断"不在这里** —— 判断在规则引擎里。

### 5.2 字段权限不归动态表单

**结论：字段权限不是动态表单的资产，不能写在它名下。**

| | 情况 |
|---|---|
| 谁**拥有**字段权限 | **流程编排**（配在流程节点上，属节点级权限）；平台级还有治理主线里的 `岗位 · 数据 · 字段` |
| 动态表单干了什么 | 它只是一个**渲染器** —— 接收别人给它的字段权限，照着渲染（隐藏／只读／可编辑） |

**渲染器不拥有被它渲染的东西。** 按这条，动态表单的三项改成 `设计器、运行时渲染、字段校验` —— 这三样才是它真拥有的：
设计器（怎么画）、运行时渲染（怎么显示）、字段校验（必填与格式）。

> 顺带解决了一个重复：之前"校验"同时挂在**动态表单**和**规则引擎**名下。现在分工清楚了 ——
> **格式与必填校验 → 动态表单**；**业务规则判定（该不该、几级、超没超） → 规则引擎**。

> **代码现状（供参考，不影响图面口径）**：字段权限在代码里是**接了**的 ——
> `NodePropertyPanel.vue` 里配（存在流程节点的 `formFields`）、`DynamicForm.vue` 里消费（`getFieldMode` 三态）、
> `WorkOrderDetail.vue` / `CreateOrderDialog.vue` 两个调用点都传了 `:permissions`。
> 如果你实测不生效，那是个 bug 而不是"没做"，可以单独查。

## 六、监测归谁 —— 六件事各归其位

"实时监测"不是一个东西，是六件事被一个词包在了一起。**逐件归位，就没有"缺一个监测引擎"的问题。**

| 你说的"监测"实际是 | 归谁 | 为什么 |
|---|---|---|
| 设备**主动上报**（烟感报警、心跳、第三方推送） | **第 2 层 · 物联设备接入** | 这是"把数据弄进来"，不是判断 |
| 业务动作**产生**事件（提交、审批通过、状态变更） | **产生它的那个引擎自己发出**（流程编排 / 台账 / 表单） | 谁改的数据谁负责广播，别设中间人 |
| 事件的**汇聚与分发** | **第 2 层 · 事件总线**（管道，不是引擎） | 它没有业务语义，只是搬运 |
| **定时**去看一眼（每 5 分钟扫设备离线、每天 8 点扫隐患逾期） | **任务调度** | 它已经在管"什么时候做" |
| **持续状态**判定（离线超 10 分钟、连续 3 次超标） | **规则引擎**（判定的一种），**记忆放在数据层** | 见下 |
| **高频时序**计算（每秒万级、滑动窗口） | **第 1/2 层技术组件**（流处理） | 技术问题，不是业务能力 |

### 关键设计：规则引擎保持"无状态"，记忆全部放数据层

"设备离线超 10 分钟"看起来需要状态，其实不需要：

```
事实（最后心跳时间 —— 存在时序数据里）
        ＋
当前时间
        ↓
   规则引擎算一下 → 结论：离线
```

**"最后心跳时间"是数据层的事实，不是规则引擎的状态。** 所以规则引擎可以始终是**无状态纯函数**：
给同样的输入永远给同样的输出，能回放、能解释（"为什么判成重大？"——把命中的条件和取到的事实摆出来就行）。

同理"连续 3 次超标"：计数器由数据层维护，规则引擎只是读它、判它。

### 要不要做一个独立的"监测引擎"？——不要

三条判据，它一条都不满足：

| 判据 | 事件总线 | 结论 |
|---|---|---|
| 有独属于它的**配置**吗？ | 没有，配的是"订阅哪些事件"，属于管道配置 | ✗ |
| 有独属于它的**状态**吗？ | 没有，状态全在数据层 | ✗ |
| 有独属于它的**变更人**吗？ | 没有，和规则是同一批业务人员 | ✗ |

更要紧的是**体验代价**：真做一个监测引擎，用户配一件事要跳三个地方 —— 监测里配"盯什么"、规则里配"怎么判"、策略里配"做什么"。**你原本担心的"零散"会立刻严重三倍。**

### 唯一值得独立的情况

如果"监测"指的是**设备接入与采集本身** —— 协议适配、采集频率、断点续传、大规模设备管理 —— 那它值得独立成产品/引擎，因为：

- 配置人是**实施与运维**，不是业务人员
- 它有独立的运行指标（连通率、采集延迟、丢包）
- 它通常**已经独立**了，就在第 2 层的"物联设备接入"里

**一句话：监测"什么时候去判断"→ 不独立（归任务调度与事件总线）；监测"怎么把设备数据收上来"→ 已经独立（归物联接入）。**

## 七、已定：指标归「统计服务」（新增第 9 个引擎）

**已定：**

- 数字台账**不含"指标"** —— 台账只管对象、关系、生命周期，不管统计口径。
- 指标独立成**第 9 个引擎「统计服务」**：`指标、口径、取数`。
- **报表引擎交出"取数"**，只做 `模板、出报、报送`。

### 为什么必须给它一个家

指标（比如"隐患逾期率"）会被**至少四处**消费：

| 消费者 | 拿指标干什么 |
|---|---|
| 数据看板 / 大屏 | 红黄绿、排行榜 |
| 报表引擎 | 月报里的数字 |
| 规则引擎 | "逾期率 > 20% 就预警"里的阈值比较 |
| 督办 / 考核 | 打分排名 |

**不指定唯一口径来源，就会出现"同一个逾期率、三张图三个数"** —— 事后最难查的一类问题。

### 拆完两个引擎都更干净

```
统计服务  →  产出「数字」  →  看板 / 大屏 / 报表 / 规则阈值 / 考核
报表引擎  →  产出「文件」  →  模板、签字、报送监管
```

产出物不同、消费者不同、生命周期不同。原来报表引擎里的"取数"其实就是统计计算的活，塞在里面反而让它的定位含糊。

### 被否掉的两个方案（记下来）

| 方案 | 为什么没选 |
|---|---|
| 并入报表引擎（`指标、取数、出报、报送`） | 一个引擎混了两种产出（数字 vs 文件）；"这个数怎么来的"要跨两个概念查 |
| 归数据层（L2 加 `指标口径`） | 口径是**计算规则**不是数据 —— "定义"有家了，"计算"还是没家 |

### 由此提炼的通用判据（可复用到别的引擎）

> **看产出物：产出「数字」的和产出「文件」的，不该塞进同一个引擎。**

## 八、状态点口径（别标错）

| 点 | 含义 | 判定依据 |

| ● | 已具备 | 有独立模块，且新业务能复用它 |

| ○ | 待建 | 没有独立模块，逻辑散落在各业务页面里 |

当前：● 流程编排、动态表单 ｜ ◐ 数字台账、消息中心、任务调度、**统计服务**、报表引擎 ｜ ○ 策略执行、规则引擎

> **统计服务为什么是 ◐ 而不是 ○**：取数能力已有真实载体（看板的取数组件、报表页），但**指标口径没有统一管理**、各页面各算各的。所以是"部分具备"，不是"完全没有"。

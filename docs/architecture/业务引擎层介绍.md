## 一、这一层是什么

**一句话：把各业务都要用的公共能力沉淀成"引擎"，让新业务靠拼装，而不是靠重写。**

放在五层里的位置：

```
第 5 层   业务域与场景层  客户在菜单上看到的功能 ← 场景是【产物】
第 4 层   交互视图层      看见什么、怎么操作
第 3 层   业务引擎层      ←──────────────────      ← 引擎是【资产】
第 2 层   数据与集成层    动什么数据、连什么设备
第 1 层   平台底座        谁都躲不掉的公共支撑
                          
```

### 判断一个能力该不该进这一层的唯一标准

> **加一个新业务时，用户是在"写配置"，还是需要"写代码"？**
>
> - 写配置就能用 → 它属于这一层的引擎
> - 必须写代码 → 要么这一层的引擎缺能力，要么它本来就不属于这一层

这条标准同时是**验收标准**。任何自称"平台化"的能力，都拿这句话测一遍。

---

## 二、这一层解决什么问题（用途）

### 2.1 没有这一层，会发生什么

| 症状 | 具体表现 |
|---|---|
| **重复开发** | 每来一个新场景（动火作业、复工复产…）就重写一套页面和后端 |
| **口径打架** | 同一个"隐患逾期率"，看板一个数、月报一个数、考核一个数，事后极难查 |
| **责任扯皮** | 权限、留痕、消息各写各的，出事时说不清哪一层该负责 |
| **成本线性增长** | 交付周期随场景数量线性增长，平台越做越重 |

### 2.2 有了这一层，变成什么

**泛化公式（一页纸就能验收）：**

```
新业务 = 台账对象 + 表单字段 + 流程节点 + 流转规则 + 校验规则 + 处置策略 + 消息模板
```

七项都能在界面上配出来 → 泛化能力是真的；
某一项必须改代码 → **那一项就是下一个要补的引擎**。

### 2.3 这一层**不**管什么（划清边界，省得扯皮）

| 不管的事 | 归谁 |
|---|---|
| 页面怎么摆、什么颜色、放哪个菜单 | 第 4 层 交互视图层 |
| 数据从哪来、存在哪、怎么同步 | 第 2 层 数据与集成层 |
| 某个行业具体怎么做业务 | 第 5 层 业务域与场景层 |
| 平台级的权限策略、审计要求、发布流程 | 第 1 层 平台底座 |
| 服务器装几台、怎么扩容、怎么备份 | 见《部署架构图》，不在能力图里 |

## 三、9 个引擎总览

| # | 引擎 | 一句话内容 | 它回答的问题 | 状态 |
|:--:|---|---|---|:--:|
| 1 | 数字台账 | 对象、关系、生命周期 | **管什么** | ◐ |
| 2 | 流程编排 | 模板、节点、流转、指派、时限 | **怎么办** | ● |
| 3 | 动态表单 | 设计器、运行时渲染、字段校验 | **填什么** | ● |
| 4 | 策略执行 | 触发、动作、留痕 | **自动做什么** | ○ |
| 5 | 规则引擎 | 条件、判定、结论 | **怎么判断** | ○ |
| 6 | 消息中心 | 模板、通道、送达回执 | **怎么通知** | ◐ |
| 7 | 任务调度 | 周期计划自动生成任务、超时催办 | **什么时候做** | ◐ |
| 8 | 统计服务 | 指标、口径、取数 | **怎么算** | ◐ |
| 9 | 报表引擎 | 模板、出报、报送 | **怎么汇报** | ◐ |

> 状态点：**●** 已具备（有独立模块且可复用）｜ **◐** 部分具备（有实做，但还不能"配置出来"）｜ **○** 待建（没有独立模块，逻辑散落在业务页面里）

**9 个引擎的分工，一句话串起来：**

> 台账管**有什么**，流程管**怎么走**，表单管**填什么**，规则管**怎么判断**，策略管**自动做什么**，消息管**怎么通知**，调度管**什么时候做**，统计管**怎么算**，报表管**怎么汇报**。

## 四、逐个引擎详解

每个引擎按同一结构说明：**定位 → 核心能力 → 谁在用 → 不归它管 → 现状**。

---

### 1. 数字台账 ◐

**定位**：把"要管的东西"从代码里搬到配置里 —— 定义一次，处处复用。

**图面文案**：`对象、关系、生命周期`

| 要素 | 含义 |
|---|---|
| 对象 | 有哪些台账要管（设备、隐患、物资、人员…） |
| 关系 | 谁属于谁、谁关联谁（设备属于哪个建筑、落在哪个点位） |
| 生命周期 | 状态怎么走（在用 → 停用 → 报废；待整改 → 整改中 → 已销号） |

**核心能力**

1. **对象建模** —— 新增一类要管的东西，不用建新表、不用写新页面
2. **关系建模** —— 一处定义、各处引用（设备 ↔ 点位 ↔ 建筑 ↔ 单位）
3. **状态机** —— 状态集合 + 允许的流转路径 + 触发条件
4. **统一编码** —— 一套编码规则贯穿全平台，避免各地各编
5. **作为其他引擎的公共参照** —— 表单的字段来源、流程的指派对象、统计的分组维度都从这里取

**谁在用**：设备台账、隐患台账、维保台账、应急物资台账、人员与组织

**不归它管**

- 统计口径怎么定 → 统计服务
- 数据怎么从设备上收上来 → 第 2 层物联接入
- 台账在页面上怎么展示 → 第 4 层交互视图

**现状**：设备台账已实做；"配置出账"的元数据驱动仍在双轨制决策中（见 [D3-台账双轨制决策.md](数字台账/D3-台账双轨制决策.md)）。

> **为什么它排第一**：它是泛化的地基。台账不能配出对象，其余 8 个引擎就只能服务写死的几种对象，泛化能力直接封顶。

---

### 2. 流程编排 ●

**定位**：把"怎么办"画成流程图 —— 谁办、多久办完都能配，改流程不用改代码。

**图面文案**：`模板、节点、流转、指派、时限`

| 要素 | 含义 |
|---|---|
| 模板 | 可复用的流程蓝图，支持复制微调与版本管理 |
| 节点 | 一个步骤 = 表单字段 + 指派规则 + 时限 + 可执行操作 |
| 流转 | 节点之间怎么跳（通过 → 下一节点，驳回 → 回到执行节点） |
| 指派 | 派给谁办（按岗位、按人、按发起人上级、按节点字段动态指定） |
| 时限 | 多久办完（双计时 + 黄灯预警 + 超时通知） |

**核心能力**

1. **可视化编排** —— 拖节点、连线、配流转条件；也支持复制现有模板微调
2. **节点级配置** —— 每个节点独立配字段、字段权限、指派规则、时限、按钮动作
3. **动态指派** —— 指派对象可以是岗位、具体人、发起人的上级、或节点上填的字段值
4. **时限与超时** —— 双计时（办理时限 / 响应时限）、黄灯阈值提醒、超时通知
5. **实例与任务** —— 模板跑起来变实例，节点派出去变某人的待办
6. **跨企业流转** —— 一件事从 A 单位流转到 B 单位（单位上报 → 监管督办 → 服务机构接单）
7. **督办** —— 超时未办的独立督办流程

**谁在用**：工单、隐患整改、动火作业审批、培训申请、演练申请、故障处置、火警处置

**不归它管**

- 判断"该不该批"的业务规则 → 规则引擎
- 超时之后自动做什么 → 策略执行（流程编排只提供"时限"和"超时事件"）
- 消息怎么发出去 → 消息中心（流程编排只声明"要通知谁"）

**现状**：已成型。设计定位即"可泛化框架，支持 90% 以上流程场景"。

---

### 3. 动态表单 ●

**定位**：把"填什么"交给业务自己画，改表单不用改代码。

**图面文案**：`设计器、运行时渲染、字段校验`

| 要素 | 含义 |
|---|---|
| 设计器 | 业务人员自己拖字段、选控件、配选项 |
| 运行时渲染 | 同一份字段定义，在不同节点渲染成不同形态 |
| 字段校验 | 必填、格式，在提交时触发 |

**核心能力**

1. **设计器** —— 拖拽字段、选控件、配选项、调布局，业务人员可自助
2. **控件集合** —— 单行/多行文本、单选、多选、下拉、开关、日期、数字、附件上传
3. **运行时渲染** —— 设计时与运行时分离开，改设计不影响在跑的实例
4. **字段校验** —— 必填、格式；**注意**：只管格式与必填，不管业务规则
5. **动态选项** —— 下拉选项可异步从接口取（比如"责任人"来自组织架构）
6. **数据回填** —— 已有数据自动带出，不用重填

**谁在用**：流程每个节点的录入与展示

**不归它管**

- **字段权限** —— 动态表单只是**渲染器**：接收别人给它的隐藏/只读/可编辑，照着渲染。权限的取值由权限体系定义、挂载在流程节点上
- 业务规则判定（"这个等级能不能直接销号"）→ 规则引擎
- 表单数据存在哪 → 第 2 层

> **一句话记住**：**渲染器不拥有被它渲染的东西。** 这条也适用于消息中心（不拥有业务规则）等所有"通道型"能力。

**现状**：设计时与运行时已分离，必填与格式校验已可用。

---

### 4. 策略执行 ○

**定位**：把"该自动做的事"固化下来，不用人盯着。

**图面文案**：`触发、动作、留痕`

| 要素 | 含义 |
|---|---|
| 触发 | 什么条件下启动（可引用规则引擎的结论） |
| 动作 | 做什么（派任务、发通知、改状态、升级给上级） |
| 留痕 | 每次自动处置都留一条可回溯的记录 |

**核心能力（设计目标）**

1. **条件触发** —— 满足条件就启动，条件可以来自规则引擎的结论或业务事件
2. **动作编排** —— 一次触发可以串多个动作：派活、通知、改状态、生成记录
3. **升级机制** —— 没人做怎么办：超时升级、逐级上报
4. **全程留痕** —— 自动做的事也要有记录，可回溯、可举证

**谁在用它（典型）**：告警自动派单、超时自动督办、隐患逾期升级、到点自动提醒

**不归它管**

- 判断本身（"该不该"）→ 规则引擎
- 流程怎么走 → 流程编排（策略执行只是发起或推动它）
- 消息怎么发 → 消息中心

**与规则引擎的分工（最容易讲混的一条）**

| | 规则引擎 | 策略执行 |
|---|---|---|
| 回答 | "**要不要**" | "**要，然后干什么**" |
| 状态 | 无状态（纯判断） | 有状态（闭环处置） |
| 副作用 | 没有 | 有 |
| 产出 | 结论 | 动作 + 记录 |

**现状**：○ 待建。目前自动处置与升级逻辑散落在各业务页面里手写。

---

### 5. 规则引擎 ○

**定位**：一直盯着某个事项，命中条件就给出**结论** —— 它只出结论，不做事。

**图面文案**：`条件、判定、结论`

| 要素 | 含义 |
|---|---|
| 条件 | 盯什么、什么算命中 |
| 判定 | 怎么算（比较、计算、时间窗口、连续次数） |
| 结论 | 算出什么（是否命中、几级、超没超、能不能提交） |

**核心能力（设计目标）**

1. **条件组合** —— 多个条件与/或组合，支持引用台账字段、表单字段、统计指标
2. **判定方式** —— 阈值比较、公式计算、时间窗口、连续次数
3. **产出结论** —— 结论是一个**数据结构**（命中了什么、几级、依据是什么），不是直接动作
4. **结论是公共数据** —— 同一份结论供**多处消费**：
   - 策略执行 → 拿它决定做什么
   - 数据看板 → 红黄绿变色
   - 报表引擎 → 统计进月报
   - 动态表单 → 字段标红
5. **无状态** —— 记忆放在数据层（最后心跳时间、计数器），规则引擎本身是纯函数：**可回放、可解释**（"为什么判成重大？"——把命中的条件和取到的事实摆出来就行）

**谁在用它（典型）**：隐患自动分级、超标预警、逾期判定、合规性校验

**不归它管**

| 事项 | 归谁 |
|---|---|
| 必填、格式校验 | 动态表单 |
| 判定之后做什么 | 策略执行 |
| 什么时候去判断（定时） | 任务调度 |
| 什么时候去判断（事件） | 事件总线（第 2 层） |
| 指标数值从哪来 | 统计服务 |

**现状**：○ 待建。判定与分级逻辑目前散落在各业务页面。

> **关于"实时监测"**：监测本身不是规则引擎的职责。规则引擎是"给我事实，我判给你看"，不负责"怎么知道有变化"。详见第六节 FAQ。

---

### 6. 消息中心 ◐

**定位**：所有触达的**唯一出口** —— 避免每个模块各写一套推送。

**图面文案**：`模板、通道、送达回执`

| 要素 | 含义 |
|---|---|
| 模板 | 发什么（内容可配，支持变量） |
| 通道 | 怎么发（站内 / 短信 / 语音） |
| 送达回执 | 发到没、失败可重试 |

**核心能力**

1. **消息模板** —— 内容可配、支持变量（谁 / 什么事 / 什么时候 / 去哪儿办）
2. **多通道** —— 站内信、短信、语音（代码里已有这三种的定义）
3. **抄送** —— 按模板抄送，或自定义抄送岗位名单
4. **送达回执** —— 能不能送到、失败了重试
5. **收口** —— 其他引擎只声明"要通知谁、用什么通道"，不自己发

**谁在用它**：流程编排（节点待办、SLA 超时通知）、策略执行（自动处置通知）、任务调度（到点提醒）

**不归它管**

- 该不该通知、通知谁 —— 由触发方决定
- **业务判断** —— 严格禁止在消息中心里写业务规则。它是通道，不是大脑

**现状**：◐ 工作台已有通知组件；节点的 SLA 超时通知配置已在流程编排里可用（通道含站内 / 短信 / 语音）；独立的"通知配置页""推送记录页"仍是占位。

---

### 7. 任务调度 ◐

**定位**：到点该做的事自动生成，不用人记得。

**图面文案**：`周期计划自动生成任务、超时催办`

**核心能力**

1. **周期计划** —— 每日 / 每周 / 每月 / 每季 / 每年
2. **任务生成** —— 到点自动把"计划"变成"具体任务"，派给责任人
3. **定时提醒** —— 提前多久提醒
4. **超时催办** —— 没做就催，可逐级
5. **定时触发** —— 同时承担"到点去跑一遍规则"的职责（规则引擎的定时触发源）

**谁在用它**：保养计划、排查计划、巡查计划、周期报表

**不归它管**：判断"该不该做" → 规则引擎

**现状**：◐ 保养计划已实做（含下次生成时间、五种周期、执行人、启停开关）；排查计划、巡查计划仍是占位。**每个模块目前各写一套，未共用。**

---

### 8. 统计服务 ◐

**定位**：同一个指标只有一个算法 —— 避免"同一张表三个数"。

**图面文案**：`指标、口径、取数`

| 要素 | 含义 |
|---|---|
| 指标 | 有哪些统计项（逾期率、整改及时率、告警数量…） |
| 口径 | 每个指标怎么算（分子、分母、时间范围、排除条件）—— **只定义一次** |
| 取数 | 按口径算出来，供各方调用 |

**核心能力**

1. **指标定义** —— 有哪些统计项，统一登记
2. **口径唯一** —— 一个指标只允许有一个算法，杜绝各页面各算各的
3. **按需取数** —— 供看板、大屏、报表、规则阈值、考核统一调用

**为什么它是独立引擎**：指标至少有 4 处消费者 —— 看板 / 大屏、报表、规则引擎的阈值、督办考核。不指定唯一口径来源，就会出现"同一个逾期率、三张图三个数"，而且事后极难查。

**与报表引擎的分工**

```
统计服务  →  产出「数字」  →  看板 / 大屏 / 报表 / 规则阈值 / 考核
报表引擎  →  产出「文件」  →  模板、签字、报送监管
```

**不归它管**：怎么展示 → 视图层；报表长什么样 → 报表引擎

**现状**：◐ 取数已有真实载体（看板 18 个统计组件、数据看板页、看板布局/校验/迁移工具）；但**指标口径没有统一管理**，各页面各算各的。所以是"部分具备"，不是"完全没有"。

---

### 9. 报表引擎 ◐

**定位**：拿统计服务的数，套模板成表，签完字直接报送监管。

**图面文案**：`模板、出报、报送`

| 要素 | 含义 |
|---|---|
| 模板 | 报表长什么样（表头、栏目、格式） |
| 出报 | 周期自动成表（月报 / 季报 / 年报） |
| 报送 | 签完字送出去（对内报告、对监管报送） |

**核心能力**

1. **报表模板** —— 表头、栏目、格式可复用
2. **周期出报** —— 到点自动生成，不用人手动整理
3. **签字确认** —— 生成后走签字，确保责任到人
4. **导出与报送** —— PDF / Excel 导出；对内报告 + 对监管报送

**谁在用它**：周期报表（对内报告 / 监管报告）、服务报告

**不归它管**：数字怎么算 → 统计服务

**现状**：◐ 报表页面已有；周期自动出报与对外报送仍是占位。

## 五、9 个引擎怎么配合（一条主链路）

```
① 事实产生      台账变更 / 表单提交 / 设备告警 / 定时到达
                        ↓
② 判定          规则引擎：条件 → 判定 → 结论        ← 纯判断，无副作用
                        ↓ 结论（可被多方消费）
③ 决定做什么     策略执行：触发 → 动作 → 留痕        ← 有副作用
                        ↓ 动作
④ 执行          流程编排派活 / 任务调度排期 / 消息中心触达
                        ↓
⑤ 结果回到台账    状态改变 → 又被 ① 捕获 → 形成闭环
```

**横向支撑**

- **统计服务** —— 把过程数据变成可复用的指标数字
- **报表引擎** —— 把指标数字变成可交付、可签字、可报送的文件

**三个"不拥有"原则**（防止引擎之间互相污染）

| 能力 | 不拥有什么 |
|---|---|
| 动态表单 | 不拥有字段权限 —— 它只是渲染器 |
| 消息中心 | 不拥有业务规则 —— 它只是通道 |
| 统计服务 | 不拥有展示方式 —— 它只出数字 |

## 六、建设状态与优先级

| 状态 | 引擎 |
|---|---|
| ● 已具备 | 流程编排、动态表单 |
| ◐ 部分具备 | 数字台账、消息中心、任务调度、统计服务、报表引擎 |
| ○ 待建 | 策略执行、规则引擎 |

**施工顺序（自上而下是优先级）**

| 优先级 | 动作 | 为什么排这个位置 |
|:---:|---|---|
| **P0** | **数字台账元数据化**（对象、关系、状态机可配） | 它决定其余 8 个引擎的上限，不解决就是"反复开发" |
| P1 | **统计服务口径收口**（指标只定义一次） | 花钱最少、见效最快；"同一指标三个数"是最伤信任的问题 |
| P1 | **规则引擎声明式化**（先做校验判定与分级，再做复杂组合） | 把散在页面里的法规要求收拢，是策略执行的前置 |
| P2 | **策略执行引擎**（触发 → 动作 → 留痕） | 依赖规则引擎 + 流程编排 + 消息中心先就位 |
| P2 | **消息中心收口 + 任务调度共用** | 消重止损，价值真实但不如前几项致命 |
| P3 | **报表引擎周期出报与报送** | 依赖统计服务先把数算准 |

> ○ 的两个（策略执行、规则引擎）是最大缺口；◐ 的五个缺的都是"**可配置**"——功能都有，只是写死在页面里。

## 七、FAQ（讲图最常被问的五个问题）

**Q1：规则引擎和策略执行是什么关系？**
A：规则引擎只回答"要不要"（无状态判断）；策略执行回答"要，然后干什么"（有状态闭环）。策略执行**调用**规则引擎做判断，再**调用**流程编排派活、**调用**消息中心通知。所以策略执行的要素是「触发、动作、留痕」，**不含"判断"**。

**Q2：字段权限归谁？**
A：归**流程编排**（配在流程节点上，属节点级权限），平台级还有 **第 1 层 平台底座 → 权限** 里的 `数据范围 · 字段级`。动态表单只是**接收并渲染**，它不拥有字段权限。

**Q3："实时监测"为什么不单独做一个引擎？**
A：因为"监测"不是一个东西，是六件事：设备上报（→ 物联接入）、业务事件（→ 产生它的引擎发出）、事件汇聚（→ 事件总线）、定时去看（→ 任务调度）、持续状态判定（→ 规则引擎，记忆放数据层）、高频时序计算（→ 技术组件）。归完位没有哪件落空。真做一个监测引擎，用户配一件事要跳三个地方，**零散会严重三倍**。
> 唯一值得独立的情况：如果"监测"指的是**设备接入与采集本身**（协议适配、采集频率、断点续传）—— 那个配置人是实施运维、有独立运行指标，**它已经独立了**，就在第 2 层物联接入里。

**Q4：指标为什么独立成统计服务，而不是放台账或报表里？**
A：因为指标有至少 4 处消费者（看板、报表、规则阈值、考核）。放台账里 → 台账是"管什么"不是"算什么"；放报表里 → 一个引擎混了两种产出（数字 vs 文件）。**判据：产出「数字」的和产出「文件」的，不该塞进同一个引擎。**

**Q5：为什么动态表单不写"字段权限"？**
A：因为它是渲染器。**渲染器不拥有被它渲染的东西** —— 字段权限的取值由权限体系定义、挂载在流程节点上，动态表单只是照着渲染。

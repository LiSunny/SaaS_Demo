## 三、研发视角：产品框架分层图

文件：[platform-dev-architecture.png](architecture/platform-dev-architecture.png) ｜ 源：[platform-dev-architecture.html](architecture/platform-dev-architecture.html)

### 3.1 这张图的三层信息结构

每个横条里都有三块，缺一不可：

```
[ 第几层 + 一句话定位 ]   [ 这一层有什么 ]   [ 给上一层什么 ]
       ↑ 是什么                ↑ 有什么            ↑ 怎么对接
```

**第三块"给上一层什么"是这张图区别于普通分层图的关键** —— 它回答"上层凭什么能用下层、换实现会不会影响上层"。

> **图面规则（2026-10-12 定）**：图上只出现中文，不出现文件路径、类名、英文标识；每层内容压缩到一句话，不堆细节。
> 想看代码位置就查下面这张对照表 —— **图给人看，表给开发查。**

### 3.2 六层逐层说明（图面说法 ↔ 代码位置）

| 图上是 | 图面定位 | 图面"给上一层" | 对应的代码位置 |
|---|---|---|---|
| **第 6 层 使用界面** | 用户看到和操作的界面 | 可以打开的页面和链接 | `src/views/**`、`src/views/bigscreen/`、`src/views/portal/` |
| **第 5 层 系统组装** | 把页面组装成一个完整系统 | 菜单、页面地址、权限 | `src/router/`、`src/config/`、`src/layouts/` |
| **第 4 层 业务功能** | 每个业务一块，写法统一 | 可以直接使用的业务页面 | `views/<域>/` + `api/<域>.ts` + `stores/<域>.ts` + `types/<域>.ts` |
| **第 3 层 平台能力 ★** | 做一次，所有业务反复使用 | 可反复使用的通用能力 | 见下表"九个业务引擎的落点" |
| **第 2 层 数据读写 ★** | 业务不直接碰后端和数据库 | 统一的数据读写方式 | `utils/dao-engine.ts`、`utils/db-adapter.ts`、`api/adapters/`、`server/src/{routes,controllers,services}/` |
| **第 1 层 运行基础** | 程序跑起来依赖的东西 | 运行环境和数据存储 | `vite.config.ts`、`server/prisma/schema.prisma`、`scripts/dev-fresh.sh` |

### 3.3 两个 ★ 是设计上最值得讲的地方

**第 2 层的"数据读写"** —— 图上那句"演示与正式可切换"，背后是全图最有含金量的一条设计：

```
src/api/<域>.ts（薄层转发，按 VITE_API_MODE 选实现）
        ├── adapters/<域>-dao.ts    localStorage / 内存 mock   ← 默认 PoC 模式
        └── adapters/<域>-http.ts   axios → 真实后端            ← VITE_API_MODE=real
                  两者接口签名一致，上层调用方一行都不用改
```

含义是：**演示环境不依赖后端就能跑通，接真后端只换适配器**。[dao-engine.ts](../src/utils/dao-engine.ts) 头部注释写得很明确："PoC 模式：接 db-adapter (localStorage)；生产模式：切到 HTTP adapter，接口签名不变"。

当前各域的实现进度（这是个可以顺手对齐的清单）：

| 状态 | 域 |
|---|---|
| **双实现齐全**（dao + http） | 工单、企业/租户、流程 |
| **只有 mock**（http 待补） | 隐患、复工复产、大屏 |
| **只有 http** | 上传 |
| 已硬编码走 mock | `src/api/work-order.ts` 里 `const adapter = dao`（注释说明后端实现后恢复模式切换） |

这条约束必须守住 —— 一旦有人在业务页面里直接 `axios.get`，这层就废了。好消息是目前 `src/views/` 下**没有任何文件 import axios**。

**第 3 层的"登记即用"** —— 图上那句"改一处全生效"，背后是同一个套路用了三处（看板卡片清单、大屏清单、权限清单）：

```
新能力 = 写一个组件 + 在注册表里登记一行
```

新增看板卡片、新增大屏类型，都不需要改调用方代码。**列表页和详情页目前还没有注册表**，这是下一步该补的。

### 3.4 讲给开发听的三句话

1. **"每层只用下面一层的东西，跨层调用就是 bug。"** 业务页面直接连数据库、组件里硬编码接口地址，都属于跨层。
2. **"带 ★ 的两层（第 2、3 层）是全团队共用的接口，改之前先打招呼；其余各层可以各自独立改。"** 数据读写方式、通用能力的对外用法，是团队协作的接口。
3. **"新功能先看底部那张扩展点表，再动手。"** 写错层是后面返工的最大来源。

### 3.5 已知的分层破例（顺手可清）

画完框架图顺手扫了一遍代码，发现一处真实的分层破例 —— 建议列进技术债：

| 破例 | 具体情况 | 影响 |
|---|---|---|
| **复工复产模块绕过了第 2 层的统一入口** | `src/views/resumption/PlanList.vue`、`PlanDetail.vue`、`steps/Step1BuildTeam.vue`、`Step2SignPledge.vue` 以及 `src/views/bigscreen/BigscreenResumption.vue` 共 **5 个视图文件**直接 `import ... from '@/api/adapters/resumption-dao'`，绕过了 `src/api/resumption.ts` 薄层 | 接真后端时这 5 个文件要逐个改；`VITE_API_MODE` 切换对它们失效 |

其余 25 个视图文件都规规矩矩走 `@/api/<域>`，所以这个破例范围很小，改造工作量不大。

### 3.6 扩展点（图底部那张表）

| 你要做什么 | 图上说的是 | 具体改哪里 |
|---|---|---|
| 新增一个业务模块 | 照现有模块复制一套，再挂进菜单 | `views/<域>/` + `api/<域>.ts` + `stores/<域>.ts` + `types/<域>.ts` + `router/index.ts` + `config/navigation.ts`（**6 处**） |
| 新增一张首页卡片 | 做一个卡片，登记进卡片清单 | 写组件 + `config/widget-registry.ts` 注册 |
| 新增一块大屏 | 做一版页面，登记进大屏清单并挂入口 | 写页面 + `config/bigscreen-templates.ts` + `router/index.ts` |
| 新增一项平台通用能力 | **放进第 3 层**：供所有业务共用 | `components/business/` 建组件，在引擎里装配，**别写进某个业务里** |
| 新增一个后端接口 | 按固定四步往后加：接请求、校验、处理、读写库 | `server/src/routes` → `controllers` → `services` → `prisma` |

## 四、产品视角：核心能力架构图

文件：[platform-architecture.png](architecture/platform-architecture.png)（横版）/ [platform-architecture-portrait.png](architecture/platform-architecture-portrait.png)（竖版）

> **业务引擎层（L3）的 8 个引擎与分层图第 3 层完全同源**，改一处两处都要同步改 —— 这是这套图的"事实底座"。

### 4.1 先记住三句话（讲图开场就用这三句）

1. **自下而上五层**：L1 跑起来 → L2 有数据 → L3 有引擎 → L4 看得见 → L5 做业务。
2. **只有 L3 是"资产"**：L3 是写一次、所有场景反复用的引擎；L5 的场景应该是 L3 **配置出来的结果**，不是新开发出来的页面。
3. **颜色点是代码实况**：● 已具备、◐ 部分具备、○ 待建 —— 标的是今天代码的真实样子，不是规划口号。

### 4.2 30 秒版话术

> "这个平台分五层。底下两层是数据和设备，中间第三层是八个业务引擎——台账、流程、表单、规则、策略、消息、调度、报表。上面两层是各角色看到的界面和业务场景。
> 关键在第三层：新来一个业务场景，比如动火作业，不该重新开发一套系统，而应该是在这八个引擎上配出来。所以这张图真正要说的是：**我们平台的价值在第三层，不在第五层。**"

### 4.3 3 分钟版（每层一句话）

| 层 | 一句话 |
|---|---|
| L5 业务域与场景层 | 客户在菜单上看到的功能，按业务域分（消防资源/风险防控/应急响应/**运营服务**/监督管理/平台运营）。本层同时承载**域级模型与规则**与**场景**，场景 ＝ 7 项配置 ＋ 域级逻辑，不是纯装配。行业解决方案包横切所有域，不占域的位置 |
| L4 交互视图层 | 工作台、大屏、列表、报表、消息 —— 同一份数据，不同人看到不同视图 |
| L3 业务引擎层 | 平台的核心资产，八个引擎配出所有场景 |
| L2 数据与集成层 | 引擎的原料：台账主数据、IoT、时序、外部系统、AI、影像 |
| L1 平台底座 | 谁都躲不掉的公共支撑 —— 任何一个客户、任何一种部署都要用 |

### 4.4 领导最可能追问的三个问题

| 追问 | 怎么答 |
|---|---|
| "这跟市面上买一套有什么区别？" | 别人卖的是 L5 的场景页面，我们攒的是 L3 的引擎。场景会被抄，引擎越用越厚。 |
| "为什么还有这么多待建？" | 待建的不是功能，是"可配置"。功能都有，只是写死在页面里了，换个场景就得重写。 |
| "先做哪个？" | 台账元数据化。它不解决，其他引擎都只能服务固定几种对象。 |

### 4.5 关于最初提的六项：归属纠偏

| 最初叫法 | 现在放在 | 调整理由 |
|---|---|---|
| 数字台账 | L3，标「泛化地基」 | 它不只是个工具，是其他引擎的对象来源，地位要抬高 |
| 流程编排 / 动态表单 | L3 | 原样保留，这两个已落地，是现有资产 |
| **规则引擎** | L3，但定位是**策略执行的零件** | 规则引擎只回答"要不要"（无状态）；策略执行要回答"派给谁、多久没做、升级给谁"（有状态）。并列会让后面互相打架 |
| **策略执行** | L3，排在规则引擎之上 | 它消费规则引擎 + 流程编排 + 消息中心三者的能力 |
| **消息中心** | L3，但标「收口」 | 它不产生业务判断，是被所有引擎调用的公共通道。打「收口」是提醒：别让业务逻辑渗进消息中心 |
| 任务调度 / 报表引擎 | L3，新增 | 原来散在各模块里，本质也是"写一次反复用"的引擎，应该显式列出 |

> **一个可以商量的地方**：严格按"主动 / 被动"分层，消息中心、报表引擎、文件影像该下沉到 L2。这张图选了"是否可配置复用"的口径，好处是"八个引擎配出所有场景"更完整。

## 六、泛化公式怎么用

```
新场景 = 挑一个业务域 + 域级模型与规则
       + 台账对象 + 表单字段 + 流程节点 + 流转规则 + 校验规则 + 处置策略 + 消息模板
```

这不是口号，是一条**验收标准**：拿一个新场景（比如"动火作业管理"）套一遍，如果**七项都能在界面上配出来**，那泛化能力在引擎层就是真的；如果某一项必须改代码，那一项就是下一个要补的引擎。

**验收边界要说明白**：七项配得出 ＝ 引擎层够用，**不等于零行代码**。本域自己的模型与规则（隐患分级、维保周期）仍要写，场景专属的取数口径也要写。判据见 [业务域与场景层介绍.md §三](应用场景层介绍.md)。

反过来也成立 —— 评估任何需求时问一句：**"这是在补引擎，还是在补场景页面？"** 补引擎排前面，补场景页面能压就压。

## 七、下一步优先级

| 优先级 | 动作 | 为什么排这个位置 |
|:---:|---|---|
| **P0** | **台账元数据化**（对象、关系、状态机、指标可配） | 它决定其余七个引擎的上限，不解决就是"反复开发" |
| P1 | 规则引擎声明式化（先做校验 + 分级，再做联动） | 把散在页面里的法规要求收拢，是策略执行的前置 |
| P1 | 视图注册表化（列表 / 详情 / 看板 registry） | 有了它，新场景的页面才是"挂上去"而不是"写出来" |
| P2 | 策略执行引擎（触发 → 处置 → 升级 → 留痕） | 依赖规则引擎 + 流程编排 + 消息中心三者先就位 |
| P2 | 消息中心收口 + 任务调度共用 | 消重、止损，价值真实但不如前三项致命 |
| P3 | 移动端 / 断网执行 | 现场无网场景的刚需，但要等数据与流程稳定后再做 |

> **给研发的补充**：L2 的"双通道适配"是这套框架能快速演示的原因，建议在代码评审里把"业务域不得直连 HTTP"写成硬规矩。

## 一、这一层是什么

**一句话：所有客户、所有部署都躲不掉的那一组能力。**

放在五层里的位置：

```
第 5 层   业务域与场景层  谁在用、用来做什么
第 4 层   交互视图层      看见什么、怎么操作
第 3 层   业务引擎层      业务规则与自动化
第 2 层   数据与集成层    动什么数据、连什么设备
第 1 层   平台底座        ←──────────────────  ← 这层：每个部署都要用
```

### 唯一的判断标准

> **任何一种部署都躲不掉 → 平台底座**
> **可能用不上 → 不叫基础设施，叫"按需启用的能力"**

拿这一条测一下：

| 候选 | 任何部署都躲不掉吗 | 结论 |
|---|:--:|---|
| 租户与组织、用户、权限、审计、配置 | 躲不掉 —— 哪怕只一个用户也得分"是谁、谁干的、留没留痕" | ✅ 进底座 |
| 服务器、数据库、网络 | 躲不掉，但它们问的是"装在哪、怎么运维" | ➖ 进部署图，不进能力图 |
| 设备接入、外部系统对接 | 躲得掉 —— 纯业务应用一个设备也没有 | ❌ 不进底座（但要保留为可选能力） |

### 与"治理主线"旧画法的关系

以前的画法是把"多租户 / 权限 / 审计 / 版本"画成**右侧的竖向条**。改完之后下沉成 L1，理由只有一个：它不是"贯穿"，是**地基**——上面四层都建在它上面。

## 二、这一层解决什么问题（用途）

### 2.1 没有这一层会怎样
- 账号/组织/单位互相乱套，分不清"是谁的设备、谁在管"
- 权限要么全有要么全没，要么靠"页面里加 if 区分"——撑不过三个业务就崩
- 出事后无法回溯到底是谁在什么时间改了什么——"尽职免责"无从谈起
- 配置散落在各个菜单，升级一次要改三处

### 2.2 有了这一层
- 平台只管"五个产品"：租户/组织、用户/身份、权限、审计、配置。每个业务都长在这五块之上
- 任意一个"对象"（隐患、设备、人员…）都自动有"谁建的、谁在管、谁能改"——因为权限/审计/组织这三块已经在底层了
- 每次配置变更都进版本库，发布时灰度、回滚都一行命令

### 2.3 这一层**不**管什么

| 不管 | 归谁 |
|---|---|
| 跑在几台机器、数据库怎么分表、备份策略 | 见 [fig3-deployment.png](fig3-deployment.png) |
| 具体的业务规则、流程怎么走、表单长什么样 | 第 2-5 层（数据 / 引擎 / 视图 / 场景） |
| 设备怎么连（MQTT/TCP/网关） | 第 2 层·可选能力 |
| 跟其他政务系统的对接通道 | 第 2 层·可选能力 |

## 四、逐组详解

每个组按：**定位 → 核心能力 → 关键实体（数据模型）→ 不归它管 → 现状**。

---

### ① 租户与组织 ●

**定位**：把"平台的客户"这件事从代码里搬到配置里——一个客户一套数据，跨客户绝对不串号。

**核心能力**
1. **多租户隔离** —— 一套平台服务多个单位（监管机构 / 社会单位 / 运营商 / 服务机构），数据按租户切分，互不可见
2. **组织层级** —— 租户下面分管理单元 / 建筑 / 重点部位，支持配置"层级最多几级"
3. **相关方关系** —— 客户、服务方、监管方之间是合同 / 监管 / 协作关系（`EnterpriseRelation`）
4. **跨租户协作** —— 隐患上报（单位→监管）、任务派发（监管→服务）必须跨租户，权限在 L3 而不是这里

**关键实体（Prisma 模型）**
- `Enterprise` 租户/企业
- `EnterpriseRelation` 租户间关系
- `UserEnterprise` 用户↔租户归属（一个用户可在多个租户）

**不归它管**
- 用户账号（→ ②）
- 单租户内的功能权限（→ ③）

**现状**：● 完整实现。`src/views/admin/Enterprise*`、`SubordinateManage`、`PartnerManage` 都已实做。

---

### ② 用户与身份 ◐

**定位**：让"我是谁"这件事从代码里搬到配置里——登录一次、按岗位换视角、跨单位也认得出来。

**核心能力**
1. **用户账号** —— 账号、密码、状态
2. **一人多单位** —— 一个人可同时在多个租户下，每个租户下有不同岗位
3. **岗位** —— 岗位是权限的载体（`Position`）
4. **登录与认证** —— JWT + bcrypt；token 写在 localStorage
5. **单点登录/第三方登录** —— 政府客户常要求走统一身份认证或对接政务 SSO
6. **人员与组织同步** —— 从上级组织同步人员、机构变动

**关键实体**
- `User` 用户
- `UserEnterprise` 用户↔租户（含在该租户下的角色）
- `Position` 岗位

**不归它管**
- 能看什么、不能看什么（→ ③ 权限）
- 单位关系（→ ① 租户与组织）

**现状**：◐ 基础完整。账号、岗位、登录、一人多单位都已实做。**缺**：
- 单点登录 / 政务对接（监管类客户常要求）
- 人员从上级组织同步
- 双因素认证

---

### ③ 权限 ◐

**定位**：把"能看到什么、能改什么"从代码里搬到配置里——业务功能不写权限判定，调用底座的统一判定。

**核心能力（三层一起管）**

| 层 | 回答 | 已实现 | 例子 |
|---|---|---|---|
| **功能模块权限** | 看得见哪些菜单/页面 | ✅ | `MODULE_GROUPS`：工作台、监控、设备、巡查、危险作业… |
| **数据操作权限** | 能不能增删改导出 | ✅ | `DATA_OPERATIONS`：列表 / 详情 / 新增 / 编辑 / 删除 / 导出 |
| **管理操作权限** | 能不能管用户/岗位/审计 | ✅ | `MANAGEMENT_OPERATIONS`：用户管理 / 企业配置 / 岗位管理 / 审计日志 |
| **数据范围权限** | 只能看自己单位的 | ◐ | 现在靠"用户归属的组织"隐含，没有显式"我看哪个租户的范围"配置 |
| **字段级权限** | 哪些字段可改 | ◐ | 字段三态已设计，挂在流程节点上 |
| **按钮级权限** | 哪些按钮可点 | ◐ | 有设计文档（`button-permissions.md`），未统一落地 |

**关键文件**
- `src/config/permission-modules.ts` — 三类权限的注册表
- `src/config/positions.ts` — 岗位与权限的对应
- `src/components/business/PermissionConfigDrawer.vue` — 权限配置 UI

**不归它管**
- 用户/账号/单位（→ ① ②）
- 业务字段在不在（→ 业务引擎层）

**现状**：◐ 三层粗粒度权限完整；细粒度（数据范围 / 字段 / 按钮）需补齐。

---

### ④ 审计与留痕 ◐

**定位**：让"出过什么事"这件事从代码里搬到配置里——只记一次"谁什么时候干了什么"，而不是每个功能各自实现一份日志。

**核心能力**
1. **操作日志** —— 谁、什么时间、做了什么、对哪个对象（`EnterpriseOperationLog`）
2. **登录日志** —— 谁、在哪台设备、什么时候登录、登了几次
3. **数据变更留痕** —— 关键数据的旧值/新值（目前各业务自己留，平台级不统一）
4. **证据链** —— 时间戳、不可篡改（按政策要求"尽职免责"要能举证）

**关键实体**
- `EnterpriseOperationLog` 操作日志

**不归它管**
- 业务过程日志（流程走到哪一步→ 在 L3 流程编排里）
- 应用错误日志（→ 图三·部署架构的日志与运行监控）

**现状**：◐ 操作日志已实做。**缺**：
- 登录日志（重要但缺失）
- 关键数据的旧值/新值留痕（各业务各做一份）
- 时间戳防篡改（目前日志可被直接编辑）

---

### ⑤ 系统配置与版本 ◐

**定位**：让"平台长什么样"和"配置怎么改版"从代码里搬到配置里——业务能自助配参数、改完还能灰度能回滚。

**核心能力（两件事）**

**A. 系统配置**
1. **数据字典** —— 国标行业分类（`gbt4754-2017`：20 门类 × 97 大类）—— 已有
2. **系统参数** —— 平台级开关、阈值、文案—— 菜单里是占位
3. **主体与品牌** —— 单位信息、主题、个性化—— 主题 store 已实现
4. **类型注册** —— 成员类型、其他自定义类型—— 已有 `MemberType` 模块
5. **编号规则** —— 台账/工单/隐患编号生成规则—— 各模块各写各的
6. **工作日历** —— 工作日/节假日定义—— **缺失**

**B. 配置版本与发布**
1. **版本** —— 模板/字典/类型等配置的修改都进版本库
2. **灰度** —— 新版本可按租户/单位灰度
3. **回滚** —— 出问题可一键回退

**关键文件**
- `src/config/gbt4754-2017.ts` — 行业分类字典
- `src/components/dashboard/DashboardShell.vue` — 大屏配置（最复杂的配置项）
- `src/views/admin/PositionList.vue`、`UserList.vue` — 平台级管理入口

**不归它管**
- 业务参数（隐患等级阈值、告警频次）→ 这些放在 L3 业务引擎层
- 流程模板的版本（→ L3 流程编排）

**现状**：◐ 基础项（字典、类型、主题）有。**缺**：
- **工作日历**（影响 SLA "2 个工作日"的计算）
- **编号规则** 统一
- **配置版本**机制（目前改了直接生效，无法回滚）

## 五、5 组怎么配合（一条主链路）

```
① 单位新增租户           （① 租户与组织）
        ↓
② 该租户有用户了         （② 用户与身份 → 关联 UserEnterprise、Position）
        ↓
③ 给岗位配权限           （③ 权限 → 业务引擎层的功能都按岗位决定看得见/改得动）
        ↓
④ 用户登录、操作业务     （④ 审计与留痕 → 每次操作自动落日志）
        ↓
⑤ 配置改版要发布         （⑤ 系统配置与版本 → 灰度、回滚）
```

**关键原则**：**底座不感知业务。** 上面四层（场景/视图/引擎/数据）任何一个挂了，底座都能独立运行。

## 六、状态与建设顺序

| 状态 | 组 |
|---|---|
| ● 已有完整实现 | ① 租户与组织 |
| ◐ 基础有但缺关键项 | ② 用户与身份、③ 权限、④ 审计与留痕、⑤ 系统配置与版本 |

**施工顺序（自上而下是优先级）**

| 优先级 | 动作 | 为什么排这个位置 |
|:---:|---|---|
| **P0** | **工作日历**（放 L1，但业务天天要用） | SLA 时限计算（"2 个工作日"）需要它；没有就"算不准" |
| **P0** | **登录日志** + **操作日志改造为不可篡改** | "尽职免责"要求证据链；这是合规线 |
| P1 | **字段级 + 按钮级权限统一落地** | 现在的"三态"在流程节点上跑得通，但各页面要自己接 |
| P1 | **单点登录 / 政务统一身份认证** | 政府客户入场必备 |
| P2 | **编号规则统一 + 配置版本与灰度** | 现在各模块各写一份；先不管版本，编号优先 |
| P3 | **人员与组织从上级组织同步** | 取决于客户使用环境 |

> ● 的只有一组（租户与组织），说明这一层一直在"凑合"。P0 里的工作日历 + 证据链是真正"必须立刻补"的。

## 七、FAQ

**Q1：为什么"设备接入"不放在这一层？**
A：按判断标准：纯业务应用的客户**一个设备也没有**。设备接入是**按需启用的能力**——不是任何部署都躲不掉。它进第 2 层·可选能力，不进底座。

**Q2：为什么"服务器/数据库/网络"不在这一层？**
A：它们问的是"装在哪、怎么运维"，不是产品能力。能力图不该有它们——否则客户看不到"我们有什么能力"，只看到一堆运维名词。它们在《部署架构图》（[fig3-deployment.png](fig3-deployment.png)）。

**Q3：原来的"治理主线"怎么变成底层了？**
A：以前画成右侧竖向条，意思是"它贯穿各层"——但这其实**弱化了它的基础性**。它不是"贯穿"，是"地基"：上面四层都建在它上面。改到底层更符合"地基"的直觉，也释放了右侧空间（之前横版的右侧条挺挤的）。

**Q4：工作日历为什么这么重要？**
A：流程时限经常写"2 个工作日办结"。如果平台没有工作日历定义，**系统算出来的是"2 个日历日"**——周末也算。结果：业务觉得你承诺的 SLA 没兑现、你以为是合规的其实没有。**这是平台底座里最容易被忘、业务天天用的一项。**

**Q5：审计留痕的"证据链"是什么？**
A：监管类的客户（教育局、应急局）在出事后，必须举证"我们尽到了告知/处置责任"。这就要求日志 **不可篡改**（不能事后删除或修改）、**带可信时间戳**。目前的 `EnterpriseOperationLog` 是普通表，库被入侵就能改——这不算"证据链"。需要做的是"**只追加、不可修改**"（append-only + hash 链 / 写独立审计库 / 第三方时间戳服务）。

**Q6：这一层和"治理"是什么关系？**
A：现在的画法是**底层**而不是**治理主线**。含义变了：
- 旧画法："治理"是**特殊功能**，贯穿各层
- 新画法："治理"是**基础设施**（权限/审计/租户/配置），和其他底层（数据库/缓存）一样是地基
- 区别在哪？——"地基"是必备的；"特殊功能"是可以选择的

# 消防水系统监测页 · 自动刷新卡顿分析与修复

页面：`/device-facility/monitor/fire-water`（`src/views/subsystem/FireWaterMonitor.vue`）
版本：commit `4f18bb4`（修复前）→ 本次改动（修复后）
日期：2026-10-28

## 结论

卡顿由**自动刷新本身**产生：每 3 秒一次刷新会在主线程制造 50–190ms 阻塞，20 次刷新中 8 次超过 50ms。停止刷新后阻塞归零。

主因是图元 SVG **每轮刷新被整体重建**，连同其中的 12 张 512×512 位图一起重新栅格化（单次约 79ms）。叠加下钻抽屉 719 行全量渲染、store 整表替换 runtime，刷新成本与"数据总量"成正比而非与"变化量"成正比。

修复后：普通页面与下钻抽屉打开时，**60 秒 20 次刷新零长任务**。

## 实测（修复前）

环境：macOS / Chrome / 生产构建 / 1x CPU。样本 = 60 秒内 20 次刷新。

| 条件 | 长任务(>50ms) | 累计阻塞 | 最差单次 |
|---|---|---|---|
| 基线（无抽屉） | 8 | 666ms | 190ms |
| 隐藏组态 12 张位图 | **0** | 0 | — |
| 关闭连线流动动画 | 3 | 237ms | 73ms |
| 打开阀门组抽屉（719 行） | 7 | 378ms | 61ms |
| 暂停刷新（15 秒窗口） | 0 | 0 | — |
| 6x CPU 降频 + 抽屉（40 秒） | 13（每次刷新都中） | 3935ms | 390ms |

6x 降频行是"假死"的等比放大：40 秒内主线程被阻塞 3.9 秒，占 25% 时间。机器再慢 3 倍即每次刷新卡 1 秒以上。

store 层单独测（Node + 真实 Vue 响应式，无 DOM，20 轮）：

| 环节 | 修复前 avg | 修复后 avg |
|---|---|---|
| `tick()` 重建点位 | 16.16ms | 11.92ms |
| 核心数据卡 computed | 2.78ms | 2.93ms |
| 组态 12 节点 computed | 3.13ms | 5.20ms |
| 报警同步 `sync()` | 0.95ms | 1.39ms |
| 合计 | 23.01ms | 21.44ms |

JS 只占刷新周期（3000ms）的 0.7%。**瓶颈不在 JS，在刷新引发的重绘与重渲染。**

数据规模：1156 点位 = 阀门 791 + 末端试水 232 + 压力 114 + 流量 6 + 液位 4 + 主机/分机 9。

## 根因

### 1 图元 SVG 每轮刷新被整体重建（主因）

`src/components/device-facility/SceneSymbolNode.vue` 原文：

```js
watch(() => [props.symbol, props.size, props.variant, props.value, JSON.stringify(props.state)], draw)
```

getter 每次返回**新数组**，引用永远不同，Vue 判定为"变化" → `draw()` 每轮刷新都执行 →

```js
el.innerHTML = src.innerHTML
```

整个 SVG 连同 12 张 `<image>` 位图被重建，浏览器必须重新栅格化。

实测（45 秒 15 轮刷新，监听底图层 DOM 变动）：

| | 修复前 | 修复后 |
|---|---|---|
| 底图层 DOM 变动次数 | 1395 | 8 |
| 位图节点替换次数 | 360 | **0** |

### 2 下钻抽屉全量渲染 719 行

`src/components/subsystem/FireWaterPointDrawer.vue` 用 `v-for` 渲染该组全部点位，每 3 秒用 `localeCompare` 重排 719 项。旧页 `SubsystemMonitorPage.vue` 有 `rendered()` 渲染上限与"导出 CSV"兜底，重构（commit `9974e5d`）时丢失。

代价：DOM 从 2717 涨到 10730 节点；抽屉打开后每次刷新阻塞 50–93ms。

### 3 store 整表替换 runtime，下游全部失效

`src/stores/subsystem.ts` 的 `tick()` 每次重建 1156 个 `PointRuntime` 及其 `values`、`trend`（约 4600 个新对象），再用 `runtime.value = next` 整体替换，组态 12 节点、4 张卡片、719 行抽屉的依赖一次性全部失效。

阀门是开关量（`src/config/subsystem-profiles.ts:43-52`，`kind: 'switch'`），791 个阀位的值几乎不变，却每 3 秒被强制重渲染；`updatedAt: Date.now()` 还给值未变化的点位盖新时间戳，下游无法判断"这个点到底变没变"。

### 4 流动动画让整图栅格无法复用（放大器）

`src/components/subsystem/FireWaterScene.vue` 的 `.fw-edge__flow` 用 `stroke-dashoffset` 无限动画。动画持续运行期间浏览器不复用已栅格化的图层，数值一改即整图重画（含 12 张位图）。关闭动画后长任务由 8 次降为 3 次。

### 5 定时器无堆积保护（放大器）

`window.setInterval(..., 3000)` 没有"上一轮未结束则跳过"的判断。单轮耗时一旦接近 3s，回调开始堆积，页面持续假死。

## 已实施的修复

| # | 改动 | 文件 | 说明 |
|---|---|---|---|
| 1 | watch 改多源数组形式 | `SceneSymbolNode.vue` | 逐项按值比较，任一项真变了才 `draw()`；位图不再每轮重建 |
| 2 | 几何与状态分离重建 | `SceneSymbolNode.vue` | 只在符号/尺寸/样式变化时重建 `innerHTML`；状态只改 class，位图节点不被替换 |
| 3 | 组态拆三层 | `FireWaterScene.vue` | 底图层（连线 + 位图，内容不变）/ 文本层（数值 + 命中区 + tooltip）/ 动画层（流动光带）。位图只光栅化一次 |
| 4 | 下钻抽屉分页 | `FireWaterPointDrawer.vue` | 每页 100 行，区间提示写清"显示到哪、总共多少" |
| 5 | runtime 改 keyed 结构 | `stores/subsystem.ts` | `reactive(new Map())`，`Map.set` 只触发该点位依赖；未变化的点位不写回 |
| 6 | `updatedAt` 仅在值变化时更新 | `stores/subsystem.ts` | 数据没变，时间戳就不变；`values` 惰性拷贝 |
| 7 | 定时器加堆积保护 | `stores/subsystem.ts` | 上一轮未结束则跳过本轮，宁可丢一轮也不堆积 |
| 8 | 报警同步改由刷新序号驱动 | `FireWaterMonitor.vue` | Map 引用不变、内容变，`watch(runtime)` 不触发，改用 `refreshSeq` |

## 复测（修复后）

同环境、同方法、同样本长度。

| 条件 | 修复前 | 修复后 |
|---|---|---|
| 普通页面 · 60 秒 20 轮 | 8 次 / 666ms / 最差 190ms | **0 次 / 0ms** |
| 阀门组抽屉 · 60 秒 20 轮 | 7 次 / 378ms / 最差 61ms | **0 次 / 0ms** |
| 6x 降频 + 抽屉 · 40 秒 | 13 次 / 3935ms / 最差 390ms | 16 次 / 2396ms / 最差 220ms |
| DOM 节点数（抽屉打开） | 10730 | 3772 |
| 底图层位图替换（45 秒） | 360 次 | **0 次** |

6x 降频下剩余的长任务是降频放大后的正常刷新成本（`tick()` 11.9ms × 6 ≈ 71ms），不是渲染缺陷。

## 更正

首版分析把"图元 SVG 每刷新重建"列为**已排除**，实际它就是主因。当时的判据写错了：`draw()` 会把元素的 class 从 `sym-node` 换成 `sym-root`，按 `sym-node` 计数统计不到重建次数。改用底图层 DOM 监听后测得 45 秒内 360 次位图替换。

你是一名资深产品经理，擅长将业务设计转化为开发团队可直接使用的详细规格文档。

$ARGUMENTS 传入要生成文档的范围，例如：
- `全部`：生成所有模块的 PRD
- `{模块名}`：只生成指定模块
- `接口设计`：只生成接口规格
- `数据模型`：只生成数据结构文档

## 执行步骤

### Step 1：读取所有设计文档
- `CLAUDE.md`：产品定位和核心规则
- `docs/design/biz-design.md`：业务流程
- `docs/design/module-plan.md`：模块清单和功能点
- `docs/issues/`：走查报告（了解已解决的问题）

确认文档的完整性：如果某模块还有未处理的 P0 问题，提示用户先运行 `/update-spec`。

### Step 2：生成产品需求文档（PRD）

为每个模块生成 `docs/prd/{模块名}.md`，结构如下：

```markdown
# {模块名} 产品需求文档

> 版本：v1.0 | 日期：{日期} | 状态：草稿

## 1. 背景与目标

### 1.1 业务背景
{来自 biz-design.md，用 2-3 句话说明为什么需要这个模块}

### 1.2 模块目标
- 用户目标：{用户通过这个模块达成什么}
- 业务目标：{这个模块支撑哪个业务指标}

### 1.3 适用范围
{哪些用户角色会使用，哪些场景下使用}

## 2. 功能规格

### 2.1 功能清单
| 功能点 | 优先级 | 说明 |
|--------|--------|------|
| {功能} | P0 | {一句话说明} |

### 2.2 详细功能说明

#### {功能点名称}

**用户故事**：作为 {角色}，我希望 {做什么}，以便 {达成什么}。

**交互说明**：
1. 用户 {操作}
2. 系统 {响应}
3. 用户看到 {结果}

**业务规则**：
- 规则 1：{具体约束}
- 规则 2：{具体约束}

**筛选条件规范**：
每个列表页的筛选条件（不含查询/重置按钮）**≤ 5 个**。超出时按使用频率分为两层：

| 层级 | 展示方式 | 说明 |
|------|---------|------|
| 常用 | 直接展示 | 高频条件（≤5 个），默认可见 |
| 折叠 | "更多筛选"展开 | 低频条件，点击按钮后展开 |

在输出筛选项时增加"层级"列（常用/折叠）。

**筛选与统计卡片重叠检查**：如果列表页同时规划了统计卡片（按状态分组计数）和状态下拉筛选，检查两者是否功能重复。统计卡片已提供点击筛选能力时，**筛选项中不应再包含同维度下拉**（如实例状态下拉）。若发现重叠，在筛选中移除该维度，并在交互说明中标注"统计卡片点击 = 同效果"。

**异常处理**：
| 场景 | 触发条件 | 系统处理 | 用户提示 |
|------|---------|---------|---------|
| {场景} | {条件} | {处理} | {提示文案} |

**验收标准（AC）**：
- [ ] AC1：{可验证的条件}
- [ ] AC2：{可验证的条件}

## 3. 数据结构

### 3.1 核心实体
```json
{
  "{实体名}": {
    "{字段名}": "{类型} | {说明} | {约束}",
    ...
  }
}
```

### 3.2 字段说明
| 字段 | 类型 | 必填 | 说明 | 约束 |
|------|------|------|------|------|

## 4. 接口设计（概要）

> 详细接口见 docs/api/{模块名}.md

| 接口名称 | 方法 | 路径 | 说明 |
|---------|------|------|------|
| {名称} | GET | /api/v1/... | {说明} |

## 5. 非功能需求

- **性能**：{关键页面加载时间、接口响应时间要求，如无特殊要求则注明}
- **兼容性**：{浏览器/设备要求}
- **安全**：{权限控制要求，如需登录、角色限制}

## 6. 待确认事项

| 问题 | 影响 | 负责人 | 截止日期 |
|------|------|--------|---------|
| {问题} | {影响范围} | PM | - |

## 7. 变更记录

| 版本 | 日期 | 变更内容 |
|------|------|---------|
| v1.0 | {日期} | 初稿 |
```

### Step 3：生成接口设计文档（如 $ARGUMENTS 包含"接口"或"全部"）

为每个模块生成 `docs/api/{模块名}.md`：

```markdown
# {模块名} 接口规格

## {接口名称}

**描述**：{做什么}
**方法**：POST / GET / PUT / DELETE
**路径**：/api/v1/{路径}
**权限**：需要登录 / 公开

### 请求参数
| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|

### 请求示例
```json
{示例 JSON，用符合业务场景的真实数据，不用占位符}
```

### 响应结构
```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

### 错误码
| code | 说明 | 处理建议 |
|------|------|---------|
| 1001 | {说明} | {前端如何处理} |
```

### Step 4：生成文档索引
更新 `docs/README.md`，列出所有已生成文档的链接：

```markdown
# 产品文档索引

## 设计文档
- [业务设计](design/biz-design.md)
- [模块规划](design/module-plan.md)

## PRD
- [{模块名}](prd/{模块名}.md)

## 接口设计
- [{模块名}](api/{模块名}.md)

## Demo
- [{模块名}](../demo/{模块名}/README.md)
```

## 输出质量要求
- 验收标准（AC）必须可测试，不能写"用户体验良好"这类模糊表述
- 异常处理表格必须覆盖所有已知边界条件
- 接口示例数据用符合业务场景的中文内容，不用 "string"、"example" 等占位
- 待确认事项不能留空，至少列出在走查过程中发现的疑问

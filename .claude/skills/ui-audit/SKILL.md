# UI 体验校验

把一个已存在的页面，当成"某岗位每天要用的工具"来验：布局合不合理、信息够不够、能不能快速发现并定位问题。
产出是**可执行的问题清单**，不是审美感想。

---

## Inputs to collect

调用前先定三件事，缺了就问用户（不要自己假设角色）：

1. **目标页面** —— 模块名 / 路由 / URL 三者给一个即可。
2. **代入角色** —— 用这个页面的人是谁（如"消控值班员""监管方安全监管员""企业管理员"）。
   用户没说，就从 `docs/平台岗位设计.md` 里选该页面的实际主使用者，并在报告开头写明。
3. **典型场景** —— 这个角色最常做的那个动作（如"夜班每 2 小时确认一次泵组状态"）。
   场景决定优先级：不在场景路径上的问题降级。

角色和场景为什么必须先定：同一个页面，值班员和监管方要的字段完全不同。
没有角色，"布局好不好"这个问题没有答案；没有场景，改进建议会跑偏成"再加些东西"。

## Procedure

### Step 1 · 定位实现

- 路由 → 文件：`src/router/index.ts` 里搜路由 path/name → 对应 `src/views/**.vue`
- 导航归属：`src/config/navigation.ts` 确认这个页面挂在哪个菜单下（决定用户实际从哪进来）
- 共享组件要一起读（如 `src/components/subsystem/`），单看页面文件会漏掉信息展示的实际规则

### Step 2 · 取三类事实（缺一不可）

| 事实 | 去哪取 | 用来判断 |
|------|--------|---------|
| **设计依据（标准答案）** | `docs/{域}/design.md`（§3 页面清单、§4 数据模型） | "信息完备"和"缺功能"的唯一依据 |
| **实现现状** | 页面 `.vue` + 子组件 + 对应 store | 实际展示了什么 |
| **项目规范** | `CLAUDE.md` §六 开发规范、`.claude/` 目录下的 `ui-patterns.md`（UI 组件实现范式） | 是否偏离范式 |

**为什么设计依据必须先读**：只看代码会把"设计文档里也没定义"误判成"实现漏做"。
缺 design.md 时，退回项目范式文件（`src/views/admin/EnterpriseList.vue` 等）作基准，并在报告里注明基准来源。

### Step 3 · 渲染取证（不要跳过）

代码看不出来的：flex 溢出、sticky 遮挡、scoped 样式被覆盖、暗色下对比度不足、真实数据量下的滚动性能。

```bash
# 确认 dev server（默认 :3200；消防三系统另跑在 :5599）
lsof -iTCP -sTCP:LISTEN -P -n | grep -E "3200|5599"
# 没有就起：npm run dev

# 采集事实（纯被动测量，不点击任何元素）
node .claude/skills/ui-audit/scripts/capture-ui.mjs \
  --url http://localhost:3200/fire/pipeline \
  --out /tmp/ui-audit --viewport 1600x1000
```

脚本产出 `<out>/facts.json` + 每页首屏/整页截图。
**必须用 `read` 工具把截图看一遍**——JSON 只有数字，布局是否协调、信息是否挤、哪里空白异常，只能看图。

> 脚本只做被动测量。交互链路（点开抽屉、筛出异常、下钻）用 Browser 工具手动走。
> **注意：页面里可能有破坏性操作（远程启动/停止、删除、批量下发），未经用户确认不要点。**

**脚本测不到、必须手动验的**（脚本只测"长什么样"，测不到"动起来对不对"）：

- 筛选/搜索是否真的生效（筛选框有值但结果没变，脚本看不出来）
- 按钮点击后有没有反馈、能不能走通主流程
- 断点隐藏：某个列在窄屏被 `display:none` 藏掉 —— 用多视口截图对比首屏；
  并确认藏它时表格**并没有横向溢出**（没有溢出也藏 = 纯信息丢失）
- 键盘可达性：从第一个输入框 Tab 到主操作按钮要几次；关闭状态的浮层/日期面板内部控件是否仍可聚焦
- 排序/分页/批量选择是否按预期
- 表格表头是否 sticky（项目范式要求 `.fi-table thead { position: sticky }`）

多视口取证用重复 `--url` + 不同 `--viewport` 分批跑，或直接改 `--viewport 1440x900` 再跑一遍。

### Step 4 · 代入式走查

按 `references/dimensions.md` 的六个维度逐项过。三个核心维度：

- **使用便捷性**：完成角色核心任务几步？热区多大？筛选作用域对不对？
- **数据完备性**：做判断需要的信息齐吗？定位/时间/责任人/阈值/趋势/聚合口径。
- **问题定位效率**：异常 3 秒能发现吗？5 秒能定位到具体那个吗？异常会不会被正常项淹没？

**代入式走查的意思**：站在角色的实际工作流里推演，不是逐个组件打分。
角色是"夜班值班员盯着屏幕找异常"时，"异常项被挤到第二屏"就是 P1；角色是"企业管理员填一次表"时，同一个问题可能只是 P2。

### Step 5 · 结论要带证据

每个维度打 0-3 分（标准见 `references/dimensions.md`），每句判断后面跟证据：
facts.json 的数字、代码行号、或"截图第 2 屏中部"。
**没有证据的"感觉不好"不写进报告。** 任一维度 0 分 → 整体不达标，不要用平均分稀释掉。

### Step 6 · 出报告

写入 `docs/issues/{模块}-ui-audit.md`（目录不存在就建），聊天里只给摘要：三句话以内最关键的问题 + 六维评分。

## Output contract

报告结构固定：

```markdown
# {页面名} UI 体验校验报告

> 代入角色：{角色} ｜ 典型场景：{场景} ｜ 校验时间：{日期}
> 设计基准：{docs/xxx/design.md §x | 项目范式文件}
> 校验方式：代码走查 + 渲染取证（{视口}）｜ 事实文件：{facts.json 路径}

## 六维评分
| 维度 | 评分 | 一句话证据 |
|------|:---:|-----------|
| 使用便捷性 | 2/3 | … |
| 数据完备性 | 1/3 | … |
| 问题定位效率 | 0/3 | … |
| 信息层级与一致性 | 2/3 | … |
| 状态与异常反馈 | 3/3 | … |
| 场景真实性 | 1/3 | … |

## 问题清单

### 🔴 P0 阻塞（角色无法完成核心任务）
1. **问题标题**
   - 现象：…
   - 证据：facts.json `alarms.inFirstScreen=1/12`；截图 `xxx.png` 第二屏
   - 复现路径：以 XX 角色进入页面 → … → 预期 vs 实际
   - 建议：…

### 🟡 P1 体验问题（主流程能走通，但明显费劲）
### 🟢 P2 优化建议
### 📋 设计文档待补充（设计文档没定义、但角色确实需要）
### ✅ 做对了的地方（保持，别在整改时误伤）
```

每条问题必须有：现象 / 证据 / 复现路径 / 建议。缺证据的条目不写。

「做对了的地方」不要省：整改时最容易连带改坏原本正确的部分（状态色语义、令牌合规、危险操作二次确认），
明确写出"这几点是对的"能防止下一轮改版误伤。

## Failure handling

| 情况 | 怎么办 |
|------|--------|
| dev server 起不来 / 端口不通 | 降级为纯代码走查，报告顶部注明"未做渲染取证"，并把"渲染验证"列入待补项。不要假装看过页面。 |
| 页面需要登录 | `capture-ui.mjs --auth auth_token=<token>`；token 从 `src/config/demo-accounts.ts` 或 `scripts/` 现有脚本里找现成写法 |
| 找不到 design.md | 用项目范式文件当基准，报告注明基准来源；不要凭"应该有"就断言缺功能 |
| 页面是 Mock 数据 | 体验结论照常出，但数据量相关结论按"生产量级待验"标注，不写成缺陷 |
| 用户只问"某个具体字段/某个按钮" | 降级回答那一个问题，不用跑全套六维 |
| 脚本在页面跑不出数据（白屏/报错） | 看 facts 里的控制台错误，先报渲染失败原因，不要基于空数据下体验结论 |

## Examples

**输入**：消防管网监测页（`/fire/pipeline`）这个页面，值班员用着怎么样？

**处理**：角色 = 消控值班员（`docs/平台岗位设计.md` 2.x）；场景 = 每 2 小时确认泵组与阀门状态；
基准 = `src/types/subsystem.ts` + 项目范式；取证 = `capture-ui.mjs --url .../fire/pipeline`；
按六维走查 → 报告落 `docs/issues/消防管网监测-ui-audit.md`，聊天里回：三句最关键问题 + 评分表。

**输入**：这个列表页信息显示全不全？

**处理**：只答"数据完备性"这一个维度（D2），先读对应 `design.md` §4 数据模型逐字段对照表头和行内字段，
缺的字段列出来；不问角色、不跑全流程。

## Windows (win32) platform notes

- 进程占用查询：`Get-NetTCPConnection -LocalPort 3200,5599 -State Listen`
- 启动前端：`npm run dev`
- 取证脚本：`node .claude\skills\ui-audit\scripts\capture-ui.mjs --url <url> --out %TEMP%\ui-audit`
- 脚本本身跨平台（Node + Playwright），Windows 下无需改动；只是命令外层要用 PowerShell 语法。

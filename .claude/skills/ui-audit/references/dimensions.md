# 维度清单 —— 每个维度查什么、怎么判定

六个维度：前三个是用户点名的核心维度，后三个是常用的补充维度。每个维度给**可判定的检查项**，
不是"感觉"。判定依据来源标注为：`代码` / `渲染` / `文档`。

---

## D1 使用便捷性（核心）

> 角色完成日常高频动作，需要多少步、多大概率点错。

| # | 检查项 | 判定标准 | 证据来源 |
|---|--------|---------|---------|
| 1.1 | **核心任务步数** | 角色最高频的那个动作（定位问题/发起处置/看某台设备），从进页面到完成几步？>3 步记为需优化 | 渲染 + 代码 |
| 1.2 | **首屏可及性** | 角色要看的第一个信息在第几屏？`facts.firstScreen` 里是否已含关键 KPI/异常 | 渲染 |
| 1.3 | **命中热区** | 可点击元素 < 32×32 px 视为过小（手指/鼠标都不友好）。`facts.interactive.tinyTargets` | 渲染 |
| 1.4 | **筛选/搜索** | 点位数量级 > 50 时，没有搜索/筛选 = 必须滚动翻找 = 不可用 | 代码 + 渲染 |
| 1.5 | **筛选作用域** | 筛选条件是"全局生效"还是"每个分区各一份输入框"？后者 = 用户搜一处，另一处不跟着变，会误以为没结果 | 代码 |
| 1.6 | **批量操作** | 角色常需要"把这一片异常的都处理了"，有没有批量选择/批量下发？ | 代码 |
| 1.7 | **输入成本** | 角色常填的东西（位置、责任单位）是不是每次都要手输？有无联想/下拉/默认值？ | 代码 |
| 1.8 | **操作位置一致性** | 详情入口在卡片右上角还是标题栏？同模块多个页面位置是否一致？ | 代码 + 渲染 |
| 1.9 | **返回成本** | 从详情回到列表，状态/滚动位置/筛选条件是否保留？ | 渲染（实际点一次） |

## D2 数据完备性（核心）

> 角色做判断需要的信息，页面给全了吗？缺一个字段就可能要打电话问人。

| # | 检查项 | 判定标准 | 证据来源 |
|---|--------|---------|---------|
| 2.1 | **定位信息** | 每条记录能否回答"这东西在哪"？至少要 位置/区域/所属主机/编号 之一，理想是编号+位置+所属主机齐全 | 代码 + 文档 |
| 2.2 | **时间信息** | 有无"数据是什么时候的"？实时页不给时间戳 → 无法判断数据新鲜度 | 代码 |
| 2.3 | **责任信息** | 出问题谁负责？所属单位/责任人/值班人/联系方式是否可得 | 文档（设计文档里定义了吗）+ 代码 |
| 2.4 | **判据信息** | 判断"正常还是异常"需要阈值/量程/标准值。缺阈值 = 用户只能凭颜色猜 | 代码 + 文档 |
| 2.5 | **趋势/历史** | 只给当前值 → 无法判断"是否恶化中"。是否给趋势曲线/历史对比 | 代码 + 渲染 |
| 2.6 | **聚合完整性** | 汇总数字与明细是否对得上（总数 = 各分区之和 = 各状态之和） | 渲染（数一遍）+ 代码 |
| 2.7 | **维度缺失** | 角色常问但页面没给的：按区域/按单位/按时间的分组对比、环比同比 | 文档 |
| 2.8 | **状态覆盖** | 6 类状态（正常/报警/故障/离线/屏蔽/未知）在页面上是否都能被区分？只给"正常/异常"两态不够 | 代码 |

## D3 问题定位效率（核心）

> 出了问题，能不能 3 秒内发现、5 秒内定位到具体那一个。

| # | 检查项 | 判定标准 | 证据来源 |
|---|--------|---------|---------|
| 3.1 | **异常不淹没** | 异常项是否被正常项挤到首屏外？`facts.alarms.inFirstScreen` 占比低于总数一半 = 定位慢 | 渲染 |
| 3.2 | **显著性** | 异常项是否只用颜色表达？纯色块 → 色弱用户/投屏/打印都看不出来。`facts.alarms.colorOnly` | 渲染 |
| 3.3 | **异常聚合入口** | 有没有"只看异常"的开关/筛选？让用户自己滚去找 = 定位效率低 | 代码 + 渲染 |
| 3.4 | **异常排序** | 默认排序是否把异常排前面？还是按编号/位置自然序，异常混在里面 | 渲染（看首屏顺序） |
| 3.5 | **下钻链路** | 从汇总数字 → 点到明细 → 点到具体点位，链路是否连贯（点汇总卡能筛出对应明细吗）？ | 渲染（实际点） |
| 3.6 | **跨页定位** | 从"工单/告警列表"点进去，能不能直接定位到出问题的那个设备，而不是回到列表自己再找一遍 | 渲染（实际点） |
| 3.7 | **异常原因直达** | 看到异常后，能否在一次点击内看到"为什么异常"（阈值对比/故障码/最近事件）？ | 代码 + 渲染 |
| 3.8 | **状态词一致** | 同一状态在汇总卡/列表/详情/告警列表里的叫法是否统一？（"报警" vs "告警" vs "火警"） | 跨页面 |

## D4 信息层级与视觉一致性（扩充）

| # | 检查项 | 判定标准 | 证据来源 |
|---|--------|---------|---------|
| 4.1 | **视觉优先级** | 最重要的信息是不是字号最大/对比最强？标题层级是否体现信息结构 | 渲染 + 代码 |
| 4.1b | **字号层级方向** | 表头字号应 ≥ 正文字号，行内标签字号应 ≤ 值字号。倒置（th 14px / td 16px）会让人扫不清列 | 渲染 + 代码 |
| 4.2 | **令牌合规** | 颜色/字号/间距是否全部走 `var(--xxx)`？硬编码色值 = 主题切换后错色 | 代码 |
| 4.2b | **孤儿样式类** | 组件挂了自定义 class（如 `fi-popper`）但全局样式里没有对应规则 → 该组件保持 Element Plus 默认外观，与平台不一致 | 代码（grep class 名 → 查 style.css 是否有规则） |
| 4.3 | **状态色语义** | 同一语义全局同色（危险=danger、警告=warning）。同页两种红/两种黄 = 误读 | 代码 + 渲染 |
| 4.4 | **信息密度** | 单屏信息单元是否超过 7±2？超了要能折叠/分页/虚拟滚动 | 渲染 |
| 4.5 | **对齐与留白** | 同类元素间距是否一致？有无贴边/重叠/错位 | 渲染 |
| 4.6 | **范式一致** | 是否偏离项目范式（`.content-card` / `.filter-bar` / `.fi-table` / `StatusTag`） | 代码 + `CLAUDE.md` §六 |

| # | 检查项 | 判定标准 | 证据来源 |
|---|--------|---------|---------|
| 5.1 | **空态** | 搜索无结果 / 无数据 / 无权限，三种空态是否区分，文案是否说清为什么 | 渲染 |

| 5.6 | **实时性提示** | 实时页是否显示"实时/已暂停/最后更新时间"？断流了用户知道吗 | 代码 + 渲染 |

## D6 场景真实性（扩充）

| # | 检查项 | 判定标准 | 证据来源 |
|---|--------|---------|---------|
| 6.1 | **使用环境** | 值班室大屏 / 工位电脑 / 手机？不同环境字号、密度、点击方式都不同 | 文档 + 渲染 |
| 6.2 | **响应式** | 1280 / 1440 / 1920 / 窄屏下是否错位？关键信息是否被挤没 | 渲染（多视口截图） |
| 6.2b | **断点是否按内容区宽** | `@media` 断点若按视口宽写，会在侧边栏展开时提前触发。若某列在断点后消失，要确认当时表格**并没有横向溢出**（scrollWidth == clientWidth）——那就是"没地方放也藏了"，属信息丢失 | 代码 + 多视口渲染 |
| 6.3 | **暗色模式** | 暗色下状态色对比度是否够（`facts.lowContrast`） | 渲染 |
| 6.4 | **数据规模** | 用真实量级数据（几百条）验，Mock 10 条看不出问题 | 渲染 + 代码 |
| 6.5 | **角色可见性** | 页面元素是否按岗位过滤？无权限元素是隐藏还是置灰/提示 | 代码 + 渲染 |
| 6.6 | **键盘可达性** | 从第一个输入框 Tab 到主操作按钮要几次？>8 次 = 键盘用户基本不可用。另查：关闭状态的浮层/面板（日期选择器、下拉）内部控件是否仍可聚焦（`offsetParent` 为 null 但 `display:block` 时会被 Tab 到） | 渲染（脚本 Tab 遍历） |

## 评分标准

每个维度打 0-3 分，必须带一句证据（引用 facts.json 数字或截图位置）。

| 分 | 含义 |
|---|------|
| **3** | 达标：角色能高效完成目标任务，无明显阻碍 |
| **2** | 基本可用：有可感知的问题，但不影响主流程 |
| **1** | 明显吃力：完成主任务需要绕路或多次试探 |
| **0** | 阻塞：核心信息缺失或核心操作走不通 |

**总评规则**：任一维度 = 0 → 整体不达标（先修 0 分维度）。不按算术平均平均掉致命问题。

## 反模式（这些不是问题，别写进报告）

- 没有走查设计文档就断言"缺功能" —— 设计文档没写 = 本次不做，不是缺陷
- 像素级挑剔（圆角 6px vs 8px）—— 没有角色影响，不记
- Mock 数据是假数据 —— POC 阶段正常，记在"待接后端"而不是体验问题
- Element Plus 默认样式 —— 项目规范本来就要求覆盖，除非覆盖后有具体问题
- 大屏场景按工位标准要求密度 —— 场景不同标准不同
